Long-term recommendation for durable checkpoint storage

3 条回复 · 2 位参与者

Ordencia Wu 询问在多租户 Flink 平台中，S3/对象存储是否会取代 HDFS 成为新部署下更推荐的持久化 checkpoint 存储，尤其关注 flink-s3-fs-native、FLIP-555 及存算分离方向对长期选型的影响。Gabor Somogyi 回应称社区正加大对 S3 的投入，趋势是减少 Hadoop 依赖，但 HDFS 仍会被继续支持，短期内不会被弃用。

@Ordencia Wu: 希望社区明确 S3/对象存储与 HDFS 在 durable checkpoint/state 存储上的长期定位，以及是否有架构演进会更偏向对象存储。

@Gabor Somogyi: S3 趋势增强，社区投入较多，原生 S3 connector 也体现了去除 Hadoop 依赖的方向，但这不代表 HDFS 支持会近期被移除。

目前没有明确宣布 S3 将取代 HDFS；两者仍将作为可选存储方案共存，用户需结合自身场景、约束和权衡来选择。

@Zakelly Lan: cobble-flink 提供 Flink 统一存储层，覆盖 managed state、source 和 sink，并支持可观察、可消费的状态与解耦存储；0.3.0-1 已发布且性能有提升。

FLIP-605: State catch-up of streaming jobs state using BATCH execution mode

1 条回复 · 2 位参与者

该讨论围绕 FLIP-605 展开，提议通过 BATCH 执行模式对流作业进行状态追赶：先以批模式处理历史/积压数据并在结束时生成 savepoint，再恢复到 STREAMING 模式继续运行，以减少长时间回放积压数据的成本。发起方表示已有可工作的早期版本，社区对该方向表示支持并提出了配置、Source 状态衔接和批阶段容错/分片 checkpoint 等问题。

@Piotr Nowojski: 提出 FLIP-605：让作业先以 BATCH 模式处理积压数据并生成 savepoint，再恢复到 STREAMING 模式继续运行，适用于 DataStream API 和 Streaming SQL/Table API。

@Xuyang: 支持该方案，并询问批阶段生成的标准 savepoint 是否可直接被流阶段恢复，以及是否仍需要在流阶段设置 execution.state-catch-up.mode: BATCH。

@Xuyang: 关注 Source 是否支持 bounded-to-unbounded 转换，并建议考虑将历史数据分片/分段执行、每段生成 checkpoint，以降低大批量回溯时的失败重算和磁盘压力。

目前讨论处于发起和初步评审阶段，社区总体支持该方向；下一步是继续围绕 FLIP 文档讨论配置语义、Source 接口兼容性和批阶段容错/分片策略等细节。

初步共识是需要改进一次性 stateless 重部署体验，但具体字段设计尚未确定；下一步是继续讨论是否采用通用 redeploy 对象方案而非单独新增 stateless nonce 字段。

FLIP-563: Support provided lib archives for YARN application mode

@Archit Goyal: 提议新增 yarn.provided.lib.archives，让 Flink 将预上传 HDFS 归档作为 public archive 资源本地化，并为每个归档添加类似 /* 的通配符 classpath，且默认不改变现有行为。

@Samrat Deb: 总体支持提案，认为 YARN PUBLIC ARCHIVE、Flink resource descriptor 和 Java launcher 通配符机制使其可行，但担心扁平通配符无法保留 flink-dist、plugin 隔离、非 jar 资源、user jar 顺序等现有语义。

@Samrat Deb: 指出通配符展开的 jar 顺序不确定，可能影响依赖顺序、重复类、SPI、日志绑定及 flink-dist 的特殊排序，并要求说明归档描述如何可靠传递到 AM 和 TaskManager。

目前尚无最终结论；下一步需要提案作者回应关于 classpath 语义、加载顺序、plugin 隔离以及 AM/TaskManager 资源传播机制的问题，并继续等待社区 review。
