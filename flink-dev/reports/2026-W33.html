Race condition in JobManager final savepoint could cause data duplication or incorrect job state, with Flink Kubernetes Operator

1 条回复 · 2 位参与者

讨论围绕 Flink JobManager 在 stop-with-savepoint 后 savepoint 路径仅保存在内存中，导致与 Kubernetes Operator 轮询之间存在竞态条件，可能造成数据重复或作业状态错误。Han You 提出在写 FLIP 前先征求意见，并给出通过持久化已终止作业信息来恢复 savepoint 路径的方案。

@Han You: stop-with-savepoint 的 savepoint 路径不会进入 CompletedCheckpointStore，若 JobManager 在 Operator 轮询前崩溃，重启后 HA 数据被清理，Operator 无法获取路径，可能从旧 checkpoint 或无状态恢复。

@Han You: 建议新增配置：jobmanager.completed-jobs.persist-dir 用于在注册 JobResultStore 前持久化全局终止作业的 ExecutionGraphInfo，以及 jobmanager.completed-jobs.persist-retention 控制保留时长。

@Han You: Dispatcher 启动时可从该持久化目录重新填充 ExecutionGraphInfoStore，从而让外部客户端通过 JobManager REST API 恢复最终 savepoint 信息。

目前处于早期方案反馈阶段，尚未形成最终结论；下一步是社区评审该原型方案，若认可则进一步撰写 FLIP。

Long-term recommendation for durable checkpoint storage

本次讨论围绕 Flink 长期持久化 checkpoint 存储的推荐方向展开，核心问题是社区是否应在 S3 与 HDFS 之间保持存储中立，以及对象存储是否因 disaggregated state 趋势而更优。参与者普遍认为 FLIP-555 和 native S3 插件只是增强云存储集成、去除 Hadoop 依赖，并不代表放弃 HDFS 或全面推荐 S3。

@Samrat Deb: 应区分两个问题：持久化 checkpoint 存储选择，以及 disaggregated state 是否更适合对象存储；FLIP-555 不改变 Flink 对 HDFS 的支持，也不推荐 S3 优于其他持久化文件系统。

@Gabor Somogyi: S3 趋势和社区投入增强，去除 Hadoop 依赖是开源大趋势，但 HDFS 仍被大量使用，短期内不会被放弃；用户应根据自身场景权衡 S3 和 HDFS。

@Ordencia Wu: 希望确认社区是否预期 Flink 在 checkpoint 存储场景下保持存储系统中立，尤其是在 S3 与 HDFS 之间。

初步结论是 Flink 社区并未将 S3 作为普遍优先推荐的持久化 checkpoint 存储，HDFS 仍受支持；下一步是继续明确不同存储方案的适用场景和权衡，由用户根据业务需求选择。
