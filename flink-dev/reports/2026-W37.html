Remove Deprecated Configuration Options/Keys in Flink

8 条回复 · 3 位参与者

本次讨论围绕在 Flink 2.x 系列中系统性移除长期废弃的配置键/兼容别名展开。Yuepeng Pan 提供了 withDeprecatedKeys 与 withFallbackKeys 的清单，并提议按废弃时间和兼容风险分批清理；Rui Fan 支持该方向。讨论进一步区分了真正废弃键与仍用于跨配置项默认值的 fallback 键，并初步明确了清理范围与风险控制原则。

@Yuepeng Pan: 提出系统性清理 Flink 2.x 中长期废弃配置键，整理了候选清单，并建议以 2025 年前最后变更的声明为初步范围；对未标记 deprecated 的 fallback 键需逐项核实，避免误删仍在使用的跨配置项默认值。

@Rui Fan: 认为这些多为 Flink 1.x 遗留配置，依据 FLIP-321 已有足够迁移时间；对于在 Flink 1.20.0 前已废弃的键，移除不存在明显兼容性风险，支持系统性清理。

@Krishna Sai: 强调必须区分 withDeprecatedKeys 与 withFallbackKeys，许多 fallback 并非旧配置名而是活跃配置间的默认引用；建议对从未正式标记废弃的键谨慎处理，并扫描确认 s3.* 等较新 fallback 应保留，web.address 可移除，schema-registry.* 需注意连接器兼容性。

初步共识是优先移除已在 2.0 release notes 中宣布移除但代码中仍保留声明的配置项，其中 web.address 可作为明确移除对象；s3.* 等较新或仍具功能性 fallback 保留。schema-registry.* 需先在相关连接器仓库处理依赖，尤其是 schema-registry.subject 仍被 flink-connector-kafka 主动使用，之后再考虑从 Flink 主仓库移除。

Flink Kubernetes Operator support for the Flink 2.3 application layer

2 条回复 · 3 位参与者

讨论围绕 Flink Kubernetes Operator 对 Flink 2.3 application 层的支持问题展开，重点分析了 stop-with-savepoint、应用结果存储清理、HA 数据清理以及 JobManager 重建之间的时序和恢复行为。参与者认为长期需要面向 application 概念的协调与清理机制，但短期需要先解决 Flink 2.3 单作业部署被阻塞的问题。

@Dennis-Mircea Ciupitu: 详细梳理了 Operator cancel/stop-with-savepoint 流程，指出 Flink 2.3 中 job 和 application result store 的异步清理顺序会影响 Operator 重新部署，建议区分 FLINK-27569 与 FLINK-40467 所需的不同修复。

@Dale Lane: 认同长期应支持 application-centric reconciliation，并认为 Flink core 提供 cleanup-complete 信号有价值；同时指出 clean application result 在恢复路径中可能阻止应用重复提交，仅修复顺序可能不足以覆盖 JM 重启场景。

@Gyula Fóra: 认为完整支持 application 概念需要较大改动并可能需要 FLIP；当前 Operator 不依赖 application 概念进行 reconciliation/cleanup，建议短期沿用现有临时方案以解除 Flink 2.3 单作业部署阻塞。

初步结论是长期应通过更大改动或 FLIP 设计 application 层清理与协调机制，短期则采用现有兼容方案先恢复 Flink 2.3 单作业部署能力；后续可继续讨论 cleanup-complete 信号和恢复语义。

[Flink CDC][postgres] JobManager connection pool exhausted after 20 incremental-snapshot jobs: JdbcSourceChunkSplitter keeps a pooled JDBC connection for the whole job lifetime

0 条回复 · 1 位参与者

邮件讨论了一个 Flink CDC PostgreSQL 增量快照作业的 Bug：自 CDC 3.3.0 引入异步分片拆分后，JdbcSourceChunkSplitter 会在整个作业生命周期内持有 JDBC 连接，导致 JobManager 侧 HikariCP 连接池被耗尽。Kyrie 报告在 3.6.0 升级后，同一数据库上运行超过 20 个增量快照作业时，第 21 个作业会因连接获取超时而持续重启。

@Kyrie: JdbcSourceChunkSplitter 在 open() 中打开 JDBC 连接，直到作业结束才关闭，导致每个增量快照作业长期占用一个连接池连接；默认连接池大小为 20，因此第 21 个作业会失败。

@Kyrie: 该问题由 FLINK-34688（异步分片拆分）引入，3.2.1 版本因每次生成 split 时使用 try-with-resources 而不受影响。

@Kyrie: 由于 ASF JIRA 账号尚未批准，建议由 committer 代为创建 issue，否则待账号批准后自行提交。

初步确认这是一个连接泄漏/资源占用问题，下一步是创建 Flink CDC JIRA ticket 并修复连接释放时机，使 JDBC 连接在分片拆分完成后及时归还连接池。
