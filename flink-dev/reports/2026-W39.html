FLINK-40234: which layer should stop busy subtask time from marking source splits idle?

1 条回复 · 2 位参与者

讨论围绕 FLINK-40234 中 Source split 空闲判定机制展开，核心问题是现有 PausableRelativeClock 在下游处理或窗口触发耗时较长时可能错误地将仍有缓冲数据的 split 标记为 idle，从而导致数据丢失。Roman 提出基于证据的空闲判定新方案，默认将 split 视为 active，只有在 Kafka 明确返回无数据且 Flink 内无缓冲记录时才判定为 idle；Sylwester 认可该方向并提出需要补充的边界场景。

@Roman Khachatryan: 提出新的 idleness 判定思路：默认 split 为 active，仅在有最近且成功的 broker 空响应、且 Flink 侧无缓冲记录时才判定为 idle，并计划后续发布 FLIP 详细设计。

@Sylwester Lachiewicz: 认同默认 active 的设计，因为漏判 idle 只会导致 watermark 停滞且可恢复，而误判 idle 会静默丢数据；并关闭了自己的原型 PR #29152。

@Sylwester Lachiewicz: 提出三点建议：需要在 FLIP 中考虑非 Kafka 数据源的通用空闲证明机制、明确“缓冲”的范围（包括正在发射的 RecordsWithSplitIds 批次）、说明默认 active 带来的用户可见行为变化。

双方初步达成共识，采用“默认 active + 证据判定”的方向，并计划通过 FLIP 推进。下一步包括：由 Roman 发布 FLIP 详细方案；讨论是否在 Flink 2.4 中引入临时修复，还是等待 FLIP 落地；Sylwester 提供 #29152 中的回归测试作为验收测试。

Clarifying the checkpoint upload path and performance attribution in the Native S3 benchmark

0 条回复 · 1 位参与者

Xia Rui 针对 Flink 社区发布的 Native S3 与 Presto S3 checkpoint 基准测试报告提出疑问，认为其中关于 Native S3 使用 S3TransferManager 实现并行非阻塞上传的架构描述与 RocksDB checkpoint 实际代码路径不一致。其核心关注点是：在 Flink 2.1.1 的 RocksDB 全量 checkpoint 场景下，SST 文件实际走的是同步 PutObject 路径，而非 TransferManager 并行 multipart 上传，因此报告中约 2 倍性能提升的归因需要进一步澄清。

@Xia Rui: RocksDB checkpoint 数据通过 RocksNativeFullSnapshotStrategy → RocksDBStateUploader → NativeS3OutputStream → S3Client.putObject 上传，属于同步 PutObject，并不会自动转为 S3TransferManager 的并行 multipart 上传。

@Xia Rui: Native S3 中基于 S3TransferManager 的上传路径仅存在于 NativeS3RecoverableWriter，例如可能用于顶层 _metadata 文件，但不能解释 RocksDB SST 文件的 checkpoint 上传性能。

@Xia Rui: 基准测试报告中关于 Native S3 架构差异和性能提升原因的描述需要澄清，尤其是究竟哪条上传路径带来了约 2 倍性能提升。

邮件尚未给出最终结论，当前处于向社区请求澄清阶段。下一步是确认基准测试中 checkpoint 上传实际使用的代码路径，并重新评估或修正性能提升的归因说明。
