Use Project Lombok in Flink beyond tests

6 条回复 · 6 位参与者

@Ferenc Csaky: 支持引入 Lombok，建议在根 POM 统一声明依赖，避免为引入 Lombok 而大规模重构，同时需更新 checkstyle 并限制实验性特性。

@Martijn Visser: 倾向反对，认为 Lombok 修补 javac 内部机制会增加 JDK 兼容负担，且后续迁移困难，建议改用 Java 17 records。

@Samrat Deb: 承认社区未达成全量采用共识，收窄提案范围，并指出 records 受 Java 11 限制，且对 Builder 或需实现特定接口的类并不完全适用。

目前未形成全代码库采用 Lombok 的共识，发起人不再推动全面引入；下一步更可能聚焦于小范围、非重构式使用，或等待/结合 Java 17 source level 升级后再评估 records 等原生替代方案。

FLIP-605: State catch-up of streaming jobs state using BATCH execution mode

1 条回复 · 2 位参与者

本次讨论围绕 FLIP-605 提出的利用 BATCH 执行模式完成流作业状态追赶（catch-up）的方案展开，重点是如何在批式追赶阶段创建和提交 savepoint，以及其对 checkpoint 超时、exactly-once sink 和并行度恢复的影响。Piotr Nowojski 对 Roman 和 Mate 提出的问题进行了回应，说明初期方案采用单个覆盖整个批式追赶阶段的 savepoint，并通过复用现有 checkpoint RPC 机制在 task 进入 RUNNING 后触发。

@Zhe Wang: 认为该方案对大规模积压数据追赶有价值，但建议在 FLIP 中明确 PendingCheckpoint 的创建时机、超时策略，以及 exactly-once sink 最终 committables 的归属和失败重试时的处理方式。

@Piotr Nowojski: 说明初期计划是整个批式追赶阶段只生成一个 savepoint，通常每个 sink 并行子任务会对应一个事务；若作业失败或取消，残留事务会通过 close/dispose 正常中止。

@Piotr Nowojski: 解释 checkpoint 触发仍复用现有 CheckpointCoordinator 的 RPC 路径，但触发时机由 task 生命周期驱动，即子任务进入 RUNNING 后再触发，而不是周期性触发。

讨论初步认可该方案的价值，但认为 FLIP 仍需补充 checkpoint/savepoint 生命周期、超时配置、exactly-once sink 事务语义以及 max parallelism/key-group 兼容性等关键细节。
