KIP-1327 Prevent Hot Data Loss on Partition Expansion for Latest Policy

7 条回复 · 3 位参与者

讨论主要针对 KIP-1327 提出的防止分区扩容时数据丢失的配置方案进行优化。Jun Rao 建议将仅针对 latest 策略的配置扩展为通用的 auto.offset.reset.new.partitions，以覆盖 by_duration 等场景。最终作者采纳建议，更新 KIP 为通过 max.age 区分新旧分区并使用独立内部配置处理新分区重置。

@Jun Rao: 指出原提案配置仅适用于 latest 策略显得局限，建议新增 auto.offset.reset.new.partitions 配置，因为 by_duration 等策略同样面临数据丢失风险。

@Chia-Ping Tsai: 提出应将 auto.offset.reset.new.partitions 设为默认值为 earliest 的内部配置，既能解决数据丢失问题，又为未来扩展留有余地。

@黃竣陽: 根据讨论更新了 KIP 设计，解耦了新旧分区的重置策略，并确认当 Broker 不支持新特性时，Consumer 将在 poll() 方法中抛出 UnsupportedVersionException。

初步结论是采纳新设计方案，引入 auto.offset.reset.max.age.ms 判定分区热度，并新增内部配置 auto.offset.reset.new.partitions（默认 earliest）专门处理新分区的位移重置。

@Matthias J. Sax: 指出 Kafka Streams 作为逻辑客户端复用物理连接，导致同一实例使用多个 ID，建议为其分配独立的逻辑 clientInstanceId 以便关联指标和配置。

@Andrew Schofield: 认为逻辑客户端概念应作为后续 KIP 而非当前 KIP 的一部分，并修改了提案以确保请求头与请求体中的 ClientInstanceId 保持一致。

@Jun Rao: 提出协议层面的疑问，询问服务端如何区分旧版本客户端缺失 ID 和新客户端显式设置零 UUID 的情况。

初步结论是将逻辑客户端 ID 的支持延后至单独的 KIP；当前 KIP 已明确请求头与请求体中 ID 必须一致，且将缺失 ID 与显式零 UUID 视为语义等价。
