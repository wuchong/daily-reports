KIP-1313: Client instance ID in all request headers

8 条回复 · 3 位参与者

讨论主要围绕 KIP-1313（在所有请求头中添加客户端实例 ID）与现有 KIP-714 遥测机制的兼容性及 ID 对齐问题展开。Andrew Schofield 更新了提案以简化版本控制并解释对齐逻辑，但 Jun Rao 指出新客户端连接旧 Broker 时可能导致服务端日志与遥测使用 ID 不一致的问题，Andrew 对此提议了强制 ID 匹配的解决方案。

@Jun Rao: 指出新客户端连接旧 Broker 时，服务端日志使用的 ID (UUID-H) 与遥测使用的 ID (UUID-B) 可能不一致，导致无法唯一识别客户端；建议增加新旧客户端与 Broker 组合的行为对照表。

@Chia-Ping Tsai: 询问若移除 RPC 负载中的重复字段，Broker 应如何处理头部和请求体均无 ClientInstanceId 的边缘情况。

@Andrew Schofield: 决定移除遥测 RPC 的新版本以避免协议兼容性噩梦，并提议强制规定若头部包含 ClientInstanceId，请求体中的 ID 必须为零或与头部 ID 一致。

Andrew 接受了关于 ID 一致性的建议，计划修改 KIP 以强制执行 ID 匹配规则，并将在达成共识后发起新的投票。

@Swathi Kumar: 发现客户端配置的 max.poll.interval.ms 仅为 50 秒（远低于默认值），建议调整空闲超时配置并开启详细日志以定位问题。

@Lucas Brutschy: 指出 connections.max.idle.ms 不会导致 StreamThread 崩溃（客户端会自动重连），且 3.4.0 版本已停止维护，建议升级。

KIP-1312: Support unregistering controllers

4 条回复 · 4 位参与者

讨论主要围绕 KIP-1312（支持注销控制器）的实现细节展开，涉及注销正在运行的 voter 的处理逻辑、错误码定义以及是否复用现有的 Broker 注销记录。作者 Kevin Wu 针对社区关于 incarnation ID、错误码命名一致性及记录复用可能引发的歧义等问题进行了详细解答，并据此更新了提案。

@David Arthur: 询问注销 voter（无论运行或离线）的具体行为及错误码，建议引入 incarnation ID 以处理控制器重新注册时的潜在副作用。

@José Armando García Sancio: 建议重构错误码命名（如改为 NODE_ID_NOT_REGISTERED）以保持一致性，并提议复用 UnregisterBrokerRecord（重命名为 UnregisterNodeRecord）来实现该功能。

@Kevin Wu: 解释了控制器注销逻辑（建议先停止 voter），确认已存在 incarnation ID；决定采用独立的 CONTROLLER_ID_NOT_REGISTERED 错误码，并坚持使用独立的注销记录以避免组合节点（combined node）场景下的歧义。

初步结论是采纳 Jun Rao 和 Kevin Wu 的建议，引入新的 CONTROLLER_ID_NOT_REGISTERED 错误码，并使用独立的注销记录而非复用 Broker 记录，作者已更新 KIP 文档。
