KIP-1313: Client instance ID in all request headers

5 条回复 · 2 位参与者

讨论主要围绕 KIP-1313 引入 RequestHeader v3 后，新客户端向旧 Broker 发送 ApiVersionsRequest 时可能引发的二进制兼容性问题展开。经过权衡，双方确认无法通过修补旧版本来解决该问题，因此决定 ApiVersionsRequest 需继续使用 v2 请求头并将 ClientInstanceId 移至请求体中。此外，讨论还确定了引入新的元数据版本（MV）以及升级 KRaft RPC 的方案。

@Jun Rao: 指出 ApiVersionsRequest v6 依赖 RequestHeader v3 会导致旧 Broker 解析失败从而断开连接，阻碍版本协商；要求在 KIP 中明确未来请求头变更的应对策略及 ClientId 的验证逻辑。

@Andrew Schofield: 确认了兼容性风险，提出将 ClientInstanceId 放入 ApiVersionsRequest 请求体但保留 v2 请求头的解决方案；反对修补旧 Broker 的方案，因为这会破坏次版本兼容性（如 4.5 客户端无法连接 3.x Broker）。

初步结论是 ApiVersionsRequest 将维持使用 v2 请求头以解决兼容性问题，同时引入新的元数据版本（MV）并升级 KRaft RPC。下一步行动是更新 KIP 文档，详细说明兼容性计划、定义 ClientInstanceId 为 0 时的 INVALID_REQUEST 错误处理，以及完善关于 ClientId 一致性的验证规则。
