KIP-1279: Cluster Mirroring

5 条回复 · 2 位参与者

讨论围绕 KIP-1279 Cluster Mirroring 的设计细节展开，重点澄清 MirrorMetadataManager 状态缓存来源，并深入辩论是否需要在 Fetch 请求中引入 MirrorLeaderEpoch。双方最终倾向于移除 MirrorLeaderEpoch，通过检测 divergeEpoch 并结合 mirror.support.unclean.leader.election 配置及新增 ULE_LOG_TRUNCATION 状态来处理源/目标集群 unclean leader election 场景。此外还讨论了 API 设计、状态查询 RPC 拆分、错误码和流程描述等细节。

@Jun Rao: 认为 MirrorLeaderEpoch 不必要：正常镜像只拉取已提交数据，不会变化；即使发生 unclean leader election，也可通过检测不一致、截断日志并等待副本追上目标 offset 来恢复，因此建议避免新增该字段。

@Luke Chen: 接受移除 MirrorLeaderEpoch，并提出实现方案：新增 ULE_LOG_TRUNCATION 状态，在启用 mirror.support.unclean.leader.election 时，检测到源集群 unclean election 导致的日志截断后暂停镜像，等待所有副本追上并降低到预期 LEO，再恢复 MIRRORING。

@Jun Rao: 建议优化 API 设计：将镜像分区状态查询与镜像 leader/lag 查询拆分，分别通过 ReadMirrorState 和 ReadClusterMirrorLags 完成，并澄清 DescribeClusterMirrorsRequest、FindCoordinatorRequest、错误码及工具调用流程。

初步结论是移除 MirrorLeaderEpoch 字段，改用 divergeEpoch 检测加配置开关与新增状态机处理 unclean leader election；下一步需更新 KIP，补充 ULE_LOG_TRUNCATION 流程、lastFetchedEpoch 行为、RPC/错误码一致性，并继续完善 Describe/Start/Stop Mirror 流程描述。
