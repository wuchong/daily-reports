KIP-1266 Bounding The Number Of RemoteLogMetadata Messages via Compacted RemoteLogMetadata Topic

5 条回复 · 3 位参与者

讨论围绕 KIP-1266 如何通过压缩（compaction）机制限制 __remote_log_metadata 主题中元数据消息数量展开，核心难点在于现有无键记录如何安全迁移到压缩主题而不丢失数据。Luke Chen 强调默认 retention.ms=-1 的用户同样需要迁移方案，Lijun Tong 认为系统无法自动判断元数据是否仍需要，最终依赖运维人员配置，Kamal 提出分阶段兼容与外部迁移脚本的方案。

@Lijun Tong: 旧无键记录可通过现有 retention.ms 自然过期，若去掉迁移中的 retention 步骤，可简化为直接检查消息格式后决定是否启用 compaction，版本仅 0/1 两种。

@Luke Chen: 认为不能接受用户因 retention.ms=-1 就不迁移，因为无人真正接受无限增长的主题；目标是让现有 -1 用户无数据丢失地迁移到压缩主题，并提出快照、重写无键记录、后台安全删除检查等思路。

@Kamal Chandraprakash: 建议新记录带 key、tombstone 放特性开关后、新主题默认 compact、旧主题不自动改策略，并提供外部脚本帮助安全迁移。

初步方向是新写入的元数据记录带 key，新集群/主题可采用 compact 策略；对存量集群不自动变更 cleanup policy，需要进一步设计安全迁移或检查机制，下一步是完善无数据丢失的迁移/校验方案。

Beam's new Kafka Streams runner: write KS applications in any Beam SDK

3 条回复 · 2 位参与者

Apache Beam 社区合并了一个实验性的 Kafka Streams runner，可将 Beam 管道转换为 Kafka Streams 拓扑，从而允许使用 Python、Go 或 YAML 等非 Java SDK 编写 Kafka Streams 应用。当前主要阻塞点是在 EOS 场景下通过 wall-clock punctuator 关闭 bundle 并转发记录时出现重复输出问题。经社区讨论后，作者认识到不应将 Beam bundle 边界与 Kafka 事务提交边界对齐，计划改为数据驱动的 flush 机制。

@Junaid: Beam 的 Kafka Streams runner 已合并，支持通过 Beam 可移植框架用多种语言编写 Kafka Streams 应用；目前在 EOS 下使用 wall-clock punctuator 关闭 bundle 会导致重复输出。

@Matthias J. Sax: EOS 主要保证输入消费、输出生产与偏移量提交的原子性，punctuation 尤其 wall-clock 类型不完全适配该模型，且 Kafka 不支持在 commit 前执行特定操作。

@Matthias J. Sax: punctuation 后只会设置 commitNeeded 标志，不存在 commitOffsetNeeded 标志；依赖事务提交边界来 flush 缓冲输出的设计不可靠。

初步结论是原设计试图对齐 Kafka Streams 不暴露的事务提交边界，方向有误；下一步将改为数据驱动的 flush 机制，由 source 发送 flush marker，各阶段在 process() 中收到标记后关闭 bundle，从而避开事务边界问题。
