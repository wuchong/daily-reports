SPIP: Distributed Map Join for Medium-Sized Build Tables

5 条回复 · 2 位参与者

Yu Gan 提出 SPIP：为 Spark 引入分布式 Map Join（DMJ）策略，解决中等规模 build 表（数百 MB 至约 10GB）与超大 probe 表 join 时因退化为 shuffle join 导致 probe 侧 shuffle 成本过高的问题。该功能默认关闭，需通过配置和 SQL hint 双重启用，且已在生产环境稳定运行两个月，可显著降低符合条件的 fact-dimension join 耗时。目前社区正在讨论其 RPC 批处理机制、分片调用粒度及最坏情况下的行为。

@Yu Gan: DMJ 将 build 侧哈希分片为可远程查询的内存分片，probe 任务通过带 Bloom filter 预过滤的批量 RPC 查询匹配行，从而避免 probe 侧 shuffle；当前批处理按 shard 粒度而非 executor 粒度，跨 executor 合并调用可作为后续优化。

@Asif Shahid: 关注 probe 侧对多个 hash 分区是否会产生 N 次调用，建议按 executor 合并请求；并询问在所有分区键都被所有 probe 节点需要的最坏情况下是否会退化为 broadcast hash join。

@Yu Gan: 澄清最坏情况不会退化为 BHJ，因为 DMJ 不在 probe 侧保存完整 build 副本，而是按需拉取匹配行；极端情况下 RPC 拓扑会变成 all-to-all，更像 shuffle 而非 BHJ。

讨论仍处于 SPIP 意见征集阶段，尚未形成最终结论。下一步是继续收集社区对整体设计和 PR 中具体问题（如 shard 基础设施是否保持 opt-in）的反馈，并可能将按 executor 合并 RPC 批次作为后续优化。
