Replacing Py4J to Spark Connect in PySpark (possibly with RDD API and UI)

8 条回复 · 6 位参与者

Hyukjin Kwon 提议在 PySpark 中用 Spark Connect 替换 Py4J 以提升安全性、性能和调试体验，并已通过原型验证了 RDD API 和 UI 支持的可行性。讨论主要围绕从直接 JVM 访问到协议边界的语义转变、第三方库的动态插件支持以及迁移策略展开。初步共识是保留 Py4J 作为备选方案，并计划在 Spark 4.3.0 中引入该功能进行测试。

@Hyukjin Kwon: Py4J 存在安全风险和性能瓶颈，Spark Connect 是更好的替代方案；已验证 Python 端 RDD API 和 UI 支持可行，且将支持插件的动态解析。

@Ángel Álvarez Pascua: 支持更整洁的协议边界，但警告这是从“Python 触达 JVM”到“协议描述”的重大语义变更，需关注现有 JVM 依赖型扩展的迁移难题。

@Dongjoon Hyun: 建议在 Spark 4.3.0 中通过特性标志引入该功能进行测试，并在后续版本（如 Spark 5）中逐步推进迁移。

初步结论是方案可行，建议在 Spark 4.3.0 中作为实验性功能（默认关闭）引入，同时保留 Py4J 作为备选以减少破坏性，后续需进一步解决动态插件加载和依赖管理问题。

SPIP: OIDC Credential Propagation

2 条回复 · 3 位参与者

讨论旨在解决 Spark on K8s 缺乏用户身份传播机制的问题，Kousuke 提议引入新的 CredentialProvider SPI 和 RPC 来支持 OIDC 凭证传播。Parth 建议先采用最小化的 DirectTokenProvider 方案解决非 Kerberos 环境，双方最终确认这两个方案互补且可并行推进。

@Kousuke Saruta: 提议引入 CredentialProvider SPI，在 Driver 端将 OIDC 令牌交换为短期凭证并通过新 RPC 分发，确保原始令牌不离开 Driver，以实现用户级授权。

@Parth Chandra: 建议优先落地最小化的 DirectTokenProvider 方案 (SPARK-27252)，以最小代码改动解决非 Kerberos 环境下的即时需求，无需引入新管理器或 RPC。

@Kousuke Saruta: 认同增量方案可行，指出 Parth 的方案解决 Pod 级身份问题，而自己的方案针对用户级身份传播，两者互不依赖，可并行开发。

双方达成共识，两个提案互为补充且互不阻塞，可以并行实施。

SPIP: Cloud Credential Refresh and Distribution Without Kerberos

0 条回复 · 1 位参与者

Parth Chandra 提议改进 Spark 的令牌分发机制，旨在消除非 Kerberos 环境下不必要的 Kerberos 限制。目前即使是像 Kafka 这样不需要 Kerberos 的令牌提供者也被强制通过 Kerberos 验证，给云环境用户带来额外负担；提案建议增加一条无需 Kerberos 关卡的路径，并保持向后兼容。

@Parth Chandra: 当前令牌分发机制强制要求 Kerberos，这对云环境（通常无 Kerberos）造成了不必要的设置门槛。

@Parth Chandra: 提议允许令牌提供者指示是否需要 Kerberos，从而绕过不必要的验证关卡。

@Parth Chandra: 该方案对现有代码改动最小，且完全向后兼容。

目前处于提案征集意见阶段，作者请求提交者审阅设计文档和 JIRA 并提供反馈。
