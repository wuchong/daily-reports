Drop Java 17 support in Apache Spark 5.0.0 (SPARK-60669)

13 条回复 · 11 位参与者

社区围绕 SPARK-60669 讨论在 Apache Spark 5.0.0 中移除 Java 17 支持，并将 Java 21 设为最低支持版本。Dongjoon Hyun 的提案获得较多支持，理由是 Java 21 已成熟、维护双版本成本高且生态正在迁移。Cheng Pan 进一步提议将最低版本提高到 Java 25，但引发对用户升级成本和兼容性的讨论。

@Dongjoon Hyun: 提议 Spark 5.0.0 移除 Java 17，将 Java 21 作为最低版本；该变更仅影响 master/5.0.0，4.x 继续支持 Java 17，并将逐步清理构建、CI、文档和 Java 17 特定代码。

@Cheng Pan: 支持移除 Java 17，但建议 Spark 5.0.0 直接以 Java 25 为最低版本，以获得 G1 Region Pinning、FFM API、原生数据源和 SIMD 向量化等性能与架构优势。

@Xiao Li: 支持 Java 21 作为最低版本，不支持 Java 25 作为最低版本；Java 21 是成熟 LTS，更利于企业用户升级，Java 25 可作为支持和推荐版本而非强制要求。

社区对移除 Java 17 并以 Java 21 作为 Spark 5.0.0 最低版本已有较明显共识；是否将最低版本提高到 Java 25 尚未达成一致。下一步预计继续推进 SPARK-60669 的构建、GitHub Actions、文档和清理工作，并对 Java 25 最低版本问题继续或单独讨论。

Run post merge builds in committers' fork

9 条回复 · 5 位参与者

讨论聚焦 Spark CI 资源紧张，尤其是合并后构建占用过高。Hyukjin 提议在 committer fork 中运行合并后构建或仅构建最新提交，但 Dongjoon 等认为会损害 committer 资源。社区随后转向探讨 merge queue、加强预合并验证、降低合并后构建频率/覆盖和增加预算等替代方案。

@Hyukjin Kwon: 提出利用 committer fork 触发合并后构建，或只对最新提交运行构建，以缓解 CI 资源压力。

@Dongjoon Hyun: 反对该方案，认为会耗尽 committer 自身 fork 的 CI 资源，影响活跃提交者生产并波及姊妹项目。

@Nicholas Chammas: 建议探索自定义 merge queue，在合并前针对最新目标分支自动测试，从而减少或取消合并后构建。

初步共识是不宜将合并后构建转移到 committer fork；下一步将评估 merge queue、强化预合并检查、精简合并后测试、增加预算或优化测试选择等方案。
