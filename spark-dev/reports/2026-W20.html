SPIP: Nano-second timestamps: micros + nanos of micro

1 条回复 · 2 位参与者

讨论主要围绕新的纳秒时间戳类型是否应严格遵循 SQL 标准年份范围（0001-9999）展开，Xiaoxuan Li 担忧这会影响 Parquet 互操作性及外部系统的输出行为。Max Gekk 回应称 Spark 已有逻辑类型与物理编码分离的先例，数据源限制应在读写边界处理，而非 SQL 类型定义中。

@Xiaoxuan Li: 若决定对新类型采用“标准优先”原则，需明确设定先例；指出 Parquet 自定义结构体会导致跨引擎互操作性丢失。

@Xiaoxuan Li: 要求 SPIP 明确超出标准范围的值在 toPandas/toArrow/Iceberg 等输出场景下的具体处理行为（如报错或截断）。

@Max Gekk: Spark 已有将 SQL 逻辑类型与物理编码分离的先例，数据源限制属于读写边界而非 SQL 类型定义。

初步倾向于维持逻辑类型与物理编码分离的设计原则，数据源层面的越界处理建议沿用现有的异常抛出机制，具体实现细节尚待进一步确认。

Decouple our CI from branch-specific logics

1 条回复 · 2 位参与者

讨论主要针对 Spark CI 中 master 分支工作流文件包含分支特定逻辑导致的耦合与不一致问题。Tian Gao 提议通过 `gh workflow run` 命令让计划任务调用特定分支的工作流文件，从而解耦各分支的 CI 逻辑。Ruifeng Zheng 对此表示支持，认为这有助于降低长期维护成本。

@Tian Gao: 现有 CI 因 master 工作流包含分支特定逻辑而产生耦合，导致不同触发方式的 CI 结果不一致。

@Tian Gao: 建议使用 `gh workflow run --ref` 让计划任务运行特定分支的工作流文件，实现解耦。

@Ruifeng Zheng: 认为这是正确的方向，长期来看能降低维护成本。

初步达成共识，将实施提议的变通方案以解耦 CI 逻辑，移除 master 分支中的特定分支逻辑。

How can we afford CI for the new release cadence?

1 条回复 · 2 位参与者

社区收到 ASF 警告，指出 Spark 项目的 CI 使用量（35万分钟/周）已超出限额（25万分钟/周），主要原因是双活跃分支导致合并后测试负载过高。Tian Gao 提出了减少测试、优化速度、智能测试及迁移定时任务等应对方案，并强调需在两周内采取快速措施将使用量降至限额以下。

@Tian Gao: 分析了 CI 超标原因，提出五种解决方案（如减少测试、优化 Java 测试速度、迁移定时任务到其他仓库等），并指出有两周时间窗口来解决问题。

@Yicong Huang: 建议将 4.x 分支的合并后测试改为每日定时运行，而非每次提交后运行，以快速削减 CI 使用量。

社区需在两周内实施临时措施（如降低测试频率）以满足 ASF 限额要求，后续再寻求长期优化方案。
