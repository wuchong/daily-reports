Spark routing architecture for Iceberg Materialized Views

0 条回复 · 1 位参与者

讨论主要关于 Iceberg 物化视图在 Spark 实现中的路由架构决策，即是在 Catalog 层还是通过独立的 Rule 逻辑进行查询路由。社区倾向于先在 Iceberg 层实现基础的替换逻辑，随后逐步让引擎根据其能力增加更复杂的优化决策。

@Walaa Eldin Moustafa: 提出了 Spark 实现物化视图时的核心问题：读时路由（read-time routing）应在何处进行，并对比了 DSv2 catalog-based routing 等方案的利弊。

@Ryan Blue: 建议首先在 Iceberg 中实现基础检查和简单的“视图替换为表读取”逻辑，这能支持无引擎环境下的 API 使用，并为后续 Spark 集成扩展打下基础。

初步结论是采用渐进式开发路径：先在 Iceberg 层实现简单路由逻辑，未来再由引擎层逐步增加复杂的优化能力。

[CORE] Pluggable SchedulingAlgorithm for the root pool (SPARK-58126)

0 条回复 · 1 位参与者

该讨论提议为 Spark 根调度池引入可插拔的 SchedulingAlgorithm 扩展点，通过新增配置项允许用户自定义排序逻辑（如基于优先级或 SLA），且在未配置时保持原有行为不变。提案采用配置文件驱动的实例化方式，以适配托管平台（如 Databricks）用户无法控制 SparkContext 创建的场景。

@Christian Neuenroth: 当前调度池的排序算法（FAIR/FIFO）硬编码在代码中，缺乏自定义扩展能力，建议通过配置项 spark.scheduler.rootPool.algorithm.class 支持自定义实现。

@Christian Neuenroth: 选择配置驱动而非运行时 Setter 方法，是因为在 Databricks 等托管平台上用户无法创建 SparkContext，配置方式更具普适性且符合 Spark 惯例。

@Christian Neuenroth: 该方案是纯增量修改，仅针对根池排序，未来可扩展支持 XML 配置的池级算法，同时需将相关接口标记为 @DeveloperApi。

提案已提交包含实现和单元测试的 PR（#57257），目前处于征求社区反馈阶段，后续将根据反馈推进该特性。
