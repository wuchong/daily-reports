SPIP: Pluggable Row-Filter and Column-Mask Enforcement in Catalyst

8 条回复 · 8 位参与者

该讨论围绕一项 SPIP 提案展开，提议为 Spark DataSource V2 增加公共访问控制 API，使表或 Catalog 能声明可读列、行过滤和列掩码策略，并由 Spark 在查询计划中强制执行。社区普遍支持该方向，认为可替代当前依赖内部 Catalyst API 的脆弱实现，但重点提出需要补充安全边界、失败关闭机制和优化器安全性等细节。

@huaxin gao: 提议新增 SupportsAccessControl DSv2 API，在分析阶段强制执行访问策略，保证掩码不会被优化器移除、行过滤使用原始值，并在无法解析时直接失败以避免泄露数据。

@Dongjoon Hyun: 支持提案方向，但要求在投票前明确安全保证，包括安全屏障、DML 读路径、旧版本兼容、绕过路径，以及将掩码不可移除表述为优化器不变量。

@Martin Grund: 认为当前提案对安全边界和执行保证描述不足，建议明确泄露表达式、类型不匹配、时间旅行等场景，并将内置掩码函数与核心提案解耦。

提案方向获得多方支持，但尚未形成最终结论；huaxin gao 表示正在整理邮件和文档中的反馈，后续将发布修订版提案文档。

SPIP: Add the DECFLOAT data type

5 条回复 · 6 位参与者

本次讨论围绕 Spark 新增 DECFLOAT 数据类型的 SPIP 展开，重点是如何区分不可逆的逻辑值域设计与可后续调整的实现细节。修订后的提案改为纯 Java 实现，解决了部分架构担忧，但在 API 完整性、Parquet 编码、算术实现方案及成熟度方面仍存在分歧，尚未达到可投票状态。

@Uroš Bojanić: DECFLOAT 应支持 IEEE 754 非有限值（+Inf、-Inf、NaN、signed zero），这是不可逆的关键设计决策；而位数和算术实现可在后续兼容地调整。

@Dongjoon Hyun: 修订版解决了原生依赖问题，但提案仍不成熟：公共 API 存在未决项、Parquet 编码未被社区接受，且当前 PR 仅为算术库移植，缺少与 Spark 引擎的集成，不建议作为独立模块合并。

@Thomas Kissinger: 质疑 IEEE BID 方案未经过充分比较，建议评估基于 BigDecimal 的有限算术包装方案，以支持 38 位精度并减少自研算术代码的维护负担。

提案方已明确 v1 仅采用纯 Java 算术路径、原生优化不在本 SPIP 范围内，并承诺公共 API 不再开放未决项；但社区普遍认为仍需完善实现集成与外部格式兼容性，后续将在 PR 代码评审中继续讨论实现细节。

Spark routing architecture for Iceberg Materialized Views

0 条回复 · 1 位参与者

讨论围绕 Spark 与 Iceberg 物化视图（MV）的路由架构展开，核心是如何在查询时选择读取物化表还是重新计算视图。Walaa 提出实现分为 Iceberg-core 元数据与新鲜度检查、以及 Spark 引擎侧路由两部分，并已基于 DSv2 catalog-based routing 和 Spark 4.2 的 loadRelation API 更新方案。Ryan 建议先从 Iceberg 内的基础检查实现起步，再逐步让引擎支持更复杂的路由决策。

@Walaa Eldin Moustafa: 实现拆分为两部分：Iceberg-core 负责物化视图元数据、源状态解析与基础新鲜度检查；Spark 侧负责引擎路由，新鲜时读取存储表，过期时评估视图查询。

@Walaa Eldin Moustafa: Spark 组件已采用 DSv2 catalog-based routing（PR #9830），并适配 Spark 4.2 的 loadRelation API，用单一调用统一返回存储表或视图，简化了旧版多路径逻辑。

@Ryan Blue: 建议先在 Iceberg 中实现基础检查，支持无引擎场景；引擎侧的复杂决策（如增量合并新数据）可后续逐步扩展，初期以“用表读替代视图”为简单路径。

初步方向是先在 Iceberg 层实现基础新鲜度检查与简单路由，Spark 侧利用 Spark 4.2 loadRelation API 统一处理新鲜/过期两种情况；后续再考虑引擎侧更复杂的优化与决策。
