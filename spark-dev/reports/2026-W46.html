Skip the CI in the master branch if the CI passed based on the latest commit in PR?

8 条回复 · 3 位参与者

讨论围绕为降低 CI 资源消耗，是否在 PR 已基于 master 最新提交通过 CI 时跳过 master 分支的重复 CI 构建。Hyukjin 调研后发现该做法在现有 master/4.x 1/10 采样 CI 机制下几乎不能节省资源，讨论最终认为收益有限。

@Hyukjin Kwon: 提议在 PR 基于最新 master 通过 CI 时跳过 master CI 以节省资源，并调研实际节省效果；后续确认现有采样机制下收益很小。

@Nicholas Chammas: 担心 master 在 PR CI 通过后继续变化可能导致合并后失败；认为在有限场景下跳过是安全的，长期更支持建设 merge queue。

@Tian Gao: 指出 master/4.x 已经采用 1/10 采样 CI，认为在此基础上进一步跳过 CI 的帮助不大。

初步结论是该优化在现有采样 CI 下节省非常有限，可能不继续推进；若长期改进 CI 策略，可考虑评估 merge queue，但当前没有明确落地行动。

SPIP: Add the OBJECT data type

2 条回复 · 3 位参与者

社区讨论为 Spark SQL 新增 OBJECT 结构化数据类型，作为 STRUCT 的按名称匹配版本，以解决 STRUCT 按位置匹配导致的插入、比较和转换风险。提案保持 STRUCT 行为不变，不引入新存储格式，并通过配置开关默认关闭，同时提供 OBJECT_APPEND、OBJECT_DELETE、OBJECT_PICK 及显式 CAST。目前该提案已获得部分成员认可，认为其能弥补 INSERT BY NAME 无法在表级别保证名称安全的不足。

@Serge Rielau: 提议新增 OBJECT 类型，使结构化对象按属性名匹配而非按位置匹配，并提供相关函数、显式 CAST 和默认关闭的配置开关。

@Xiao Li: 认可提案动机，认为当前表所有者无法在写入、比较等表达式中强制名称安全，仅靠 INSERT BY NAME 不足以解决该问题。

@Daniel Tenedorio: 支持按名称引用字段，认为 STRUCT 默认按位置匹配的行为可能令人意外。

初步反馈积极，但尚未形成最终结论；下一步继续收集关于问题描述、命名和被否决备选方案的意见，并按 SPIP/JIRA 计划推进，预计开发周期约 3 个月。
