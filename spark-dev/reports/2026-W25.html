Eliminating startup time in local dev/test loop

8 条回复 · 3 位参与者

讨论旨在消除 Spark Connect 本地开发循环中的启动时间。核心争议在于是否应隐式启动持久化服务器，最终参与者倾向于“显式同意”方案，即用户手动启动服务器而客户端仅负责发现连接，以规避状态混乱风险。

@Holden Karau: 担心隐式持久化服务器会导致用户困惑（例如重启 Python 进程并未杀掉服务器），建议提供清晰的用户指引。

@Tian Gao: 反对将隐式持久化服务器作为默认行为，认为这会引入非确定性行为和难以调试的状态问题，支持仅在用户显式请求时启用。

@Nicholas Chammas: 提议采用“较弱”方案，即添加 CLI 工具并让 `.remote("local")` 自动发现现有服务器，但不自动创建或管理服务器。

初步达成一致，将实施“较弱”方案：提供 CLI 和文档支持，允许 `.remote("local")` 发现并连接已显式启动的服务器，避免改变现有默认行为。

SPIP: Cloud Credential Refresh and Distribution Without Kerberos

8 条回复 · 3 位参与者

讨论主要围绕 SPIP "Cloud Credential Refresh and Distribution Without Kerberos" 展开，旨在移除 Spark 获取云存储委托令牌时对 Kerberos 的强制依赖。参与者深入探讨了该方案与 OIDC 凭据传播 SPIP 的功能重叠问题，以及 JDK 22+ 中 Subject 传播变更对 Spark K8s 模式下凭据分发的潜在影响。

@Steve Loughran: 指出 Hadoop 委托令牌接口本身不依赖 Kerberos，问题在于 Spark 仅在启用安全机制时才请求令牌，建议将安全检查设为可选。

@Cheng Pan: 认为两个 SPIP 并存会导致功能冗余和诊断困难，倾向于 OIDC 方案；并指出 JDK 25 的变更会破坏线程间 Subject 传播，影响凭据访问。

@Parth Chandra: 解释本 SPIP 旨在以最小代码变更移除 Kerberos 门槛，声称其 DirectProviderPath 方案不受 JDK 变更影响（遭 Cheng Pan 反驳）。

尚未达成明确共识。Cheng Pan 对方案独立性提出异议并指出了 JDK 25 兼容性漏洞，后续需进一步讨论两个 SPIP 的取舍及 HADOOP-19906 补丁的整合。

@Nicholas Chammas: 新的统一 CLI 将基于 Python 标准库，作为调度器整合现有脚本，提供清晰的帮助信息。

@Nicholas Chammas: 仍需解决打包方式、命令命名结构以及是否最终将 Bash 脚本合并入 Python CLI 等细节问题。

目前处于提案征集意见阶段，作者已发布原型演示，等待社区（特别是 Committer）反馈以决定是否创建正式工单。

Nested-field pruning extension through explode (SPARK-47230)

0 条回复 · 1 位参与者

Igor Berman 提议扩展 Spark 的嵌套字段剪枝功能，旨在解决链式 explode 和仅取位置的 posexplode 场景下 I/O 开销过大的问题。他建议引入新的 Catalyst 优化器规则和 NestedArraysZip 表达式，在扫描阶段进行剪枝，并提供了生产环境的性能测试数据作为支持。

@Igor Berman: 现有 NestedColumnAliasing 机制在处理链式 explode 或仅取位置的 posexplode 时无法有效剪枝，导致读取大量无用数据。

@Igor Berman: 提议新增默认开启的 Catalyst 规则，配合 NestedArraysZip 表达式重建数组，且不影响现有已覆盖的场景。

@Igor Berman: 实测显示该优化能将单任务读取量从 200+ GB 降至 20-30 GB，达到理论 I/O 下限。

作者正在征求社区对变更方案形态的意见，以便后续推进深入代码审查。
