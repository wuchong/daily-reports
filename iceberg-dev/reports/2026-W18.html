6 条回复 · 5 位参与者

@Kurtis Wright: 提议在多个层级添加校验和以确保持久性和完整性，并倾向于将其设计为可选功能而非默认强制。

@Andrei Tserakhau: 支持该提议，指出在生产环境中确实观测到了现有校验机制无法捕获的数据损坏问题，格式层校验能提供额外保障。

发起人将提交一份正式提案，建议将校验和作为可选功能，以进一步评估其在生产环境中的价值。

REST Catalog: Credential management for KMS/Vault and Table level Encryption

4 条回复 · 5 位参与者

讨论核心在于 REST Catalog 中存储凭证与 KMS/加密凭证的管理方式是否应分离，以及当前 PR 是否应包含服务端凭证分发机制。虽然大家一致认为应解耦这两类凭证，但在当前 PR 是仅作为基础脚手架先行合并，还是应等待完整的凭证分发设计上存在不同意见。

@Chris Lu: 建议将存储凭证和加密凭证分开，因为二者范围、生命周期和故障模式不同，并提出可使用类型化凭证模型以便扩展。

@Prashant Singh: 反对当前 PR 仅从客户端获取加密凭证而服务端分发存储凭证的做法，认为服务端应负责分发所有必要凭证以保证权限模型的一致性。

@Ádám Szita: 认为支持表加密与定义 KMS 凭证分发机制是两个独立话题，不应强制要求 REST Catalog 实现凭证分发才能支持加密，以免阻碍现有功能。

初步结论是需要在规范层面将 KMS 凭证与存储凭证解耦。下一步建议是不要急于合并代码，需先明确规范变更和凭证分发的设计细节。

Efficient column updates in Iceberg

4 条回复 · 4 位参与者

讨论主要聚焦于 Iceberg 部分更新功能的文件表示形式选择。社区已决定采用“完整/密集”表示法以简化写入逻辑，而非稀疏表示法。目前仍需解决当基文件包含删除行时，更新文件应如何对齐或填充数据的开放性问题。

@Gábor Kaszab: 确认选择密集表示法，因为稀疏表示在合并多次字段更新时极其复杂，且密集方案的 PoC 显示其性能优于现有 MoR。

@Péter Váry: 支持密集表示，因为行数对齐的文件能极大简化向量化读取器的数据拼接过程，避免稀疏转换开销。

@Gang Wu: 提出担忧，认为密集文件可能增加 SQL 计划的复杂性（需读取旧值或额外元数据），可能抵消写入加速的优势。

已确定部分更新采用“完整/密集”表示法；下一步将重点讨论如何处理基文件中已删除行的表示方式（如填充辅助值或跳过），以及是否需要分发行数元数据。

metadata.json in v4?

3 条回复 · 3 位参与者

讨论主要关注 metadata.json 在读取路径上造成的内存压力问题，特别是在 Trino 协调器缓存大量表元数据时。Grant 提议对 snapshotLog 实施延迟加载以缓解堆内存占用，并提交了原型 PR，讨论随后扩展到了快照压缩和缓存策略权衡等解决方案。

@Grant Nicholas: 指出流式负载下 snapshots 和 snapshotLog 线性增长导致内存压力，提议对 snapshotLog 实施延迟加载，并建议短期优化读取路径，长期探索快照压缩等方案。

@Amogh Jahagirdar: 支持改进但指出时间旅行查询需加载日志会限制优化效果，建议对于高频写入表考虑直接查询目录而非缓存元数据，并明确此问题非 V4 特有而是实现层面的改进。

@Péter Váry: 提出“选择性快照压缩”的概念，建议通过合并历史快照来减少元数据中需要保留的快照数量。

初步确定短期方案为优化读取路径（如延迟加载），长期将探索选择性快照压缩、分离存储以及 REST catalog 改进等措施。

Partition tuples in v4

@Russell Spitzer: 建议暂时保留 partition tuple 以满足 equality deletes 的需求，但在 V4 代码中应隔离对其访问，为后续移除并转向 stats 方案做准备。

@Steven Wu: 同意暂时保留 partition tuple，并主张将其仅限于 equality deletes，同时扩展 stats 方法以覆盖非单调分桶和多参数转换。

@Micah Kornfield: 询问针对 Hive 表迁移的列投影边缘情况，应使用 tuple 还是 stats 处理 Identity 分区列。

初步结论是暂时保留 partition tuple，下一步行动包括在 V4 代码中隔离 tuple 访问逻辑，并致力于扩展 stats 结构以替代 tuple 进行过滤。
