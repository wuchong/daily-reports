Column Updates: Row Group alignment optimization

11 条回复 · 8 位参与者

讨论围绕 Iceberg Column Updates 中是否需要在元数据中增加行组对齐标志（如 ColumnFile.containsAlignedRowGroups）以优化读取性能。提议者认为对齐可实现零拷贝读取并减少 I/O 开销，但多数参与者认为读取器可在读取时通过比较 Base File 和 Column File 的 footer 来判断对齐情况，且已有 splitOffsets 机制可用于扫描规划，因此无需额外元数据标志。最终社区倾向于不引入该标志，而由读取器在运行时自动优化。

@Leonid Lygin: 提议增加元数据标志标识行组对齐，以支持零拷贝读取、减少 I/O 和内存开销，并强调该优化对写入器和读取器均为可选。

@Russell Spitzer: 认为读取器在读取时可通过比较两个文件的 footer 判断行组是否对齐，无需在 Iceberg 元数据中提前声明；应避免在元数据层做格式特定的性能优化。

@Anoop Johnson: 支持 Russell 的观点，指出 splitOffsets 已提供扫描规划所需的偏移信息，行组对齐可在读取 footer 后通过简单整数比较得出，无需额外标志。

初步共识是不引入行组对齐的元数据标志，因为读取器可在运行时通过 footer 比较和 splitOffsets 实现对齐判断与读取优化；是否写入对齐的行组可由实现自行决定，暂不纳入规范。Ryan Blue 建议不在设计文档中加入该细节以避免复杂化，Anurag Mantripragada 表示将更新设计文档反映近期决定。

V3 to V4 upgrade expectations and migration practices

9 条回复 · 7 位参与者

本次讨论围绕 Iceberg V3 到 V4 的升级路径展开，核心关注点是升级后旧版 manifest 的生命周期管理以及用户迁移体验。社区普遍支持 O(1) 轻量级升级设计，即保留旧 manifest、新写入采用 V4 格式，但同时也认识到需要明确文档指导，避免用户对“升级到 V4”后的实际收益产生误解。

@Shawn Chang: 担忧轻量升级后旧 manifest 长期留存，若缺乏明确规范或指导，会将迁移责任转嫁给用户；建议社区明确文档说明混合版本元数据的行为与限制。

@Anoop Johnson: 支持 O(1) 升级设计以避免高成本元数据重写带来的升级阻力，倾向于通过指导和维护工具逐步迁移，而非强制规范升级协议。

@Russell Spitzer: V4 读取器必须兼容读取 V1-V3 元数据；元数据迁移属于实现层面决策，无需规范强制；可考虑在 V5 设置兼容性断点。

初步共识是保持规范开放性，允许实现自行决定迁移策略；下一步建议由实现方明确其迁移行为，社区补充文档说明混合版本元数据的预期行为与局限，并可考虑在 V5 引入兼容性边界。

should V4 manifests be Parquet-only?

7 条回复 · 5 位参与者

Iceberg 社区讨论是否将 V4 manifest 文件限定为仅支持 Parquet 格式，以提升投影读取和扫描规划性能，并降低规范与实现复杂度。多数参与者倾向 Parquet-only，但也有声音建议保留多格式灵活性以避免生态绑定风险。

@Steven Wu: 提出 V4 manifest 应仅使用 Parquet，以减少集成方的选择负担并提升读取性能；同时澄清本次讨论只针对 manifest 文件，不涉及数据文件格式。

@Anoop Johnson: 支持 Parquet-only，认为可简化规范和实现；指出当前未跟踪 root manifest 格式，且 V4 升级仍需兼容已有的 v3 Avro leaf manifest。

@Péter Váry: 担忧过度绑定单一文件格式可能限制未来演进，倾向保留多格式基础设施；但表示如果社区偏好，不反对移除 Avro 元数据格式。

初步共识倾向于将新的 V4 manifest 限定为 Parquet-only，同时继续支持读取升级前版本中的 Avro manifest；后续需进一步收集社区反馈并确认规范实现细节。

AI Review comments

@Manu Zhang: AI 生成的评审评论往往冗长且可能相互冲突，直接发布会增加审查负担；建议先阅读 AI 发现，筛选有效问题后由人工整理并发布。

@Junwang Zhao: 认同不应在未理解 AI 评论前发布，但如果 AI 表述更清晰可保留原措辞；不过该原则在实践中较难强制执行。

@vaquar khan: 提出通过更新 AGENTS.md 规范 AI 使用：人工对每条评论负责、避免将 AI 工具写成 Co-authored-by、限制 AI review agent 权限，并要求 AI 生成的 PR 经过同样审核、测试和安全流程。

[Iceberg v4] null_value_count is only for optional field?

2 条回复 · 3 位参与者

社区讨论了 Iceberg v4 中 null_value_count 是否仅适用于 optional 字段的问题，核心争议在于嵌套 required 字段在其父级为 optional 时是否应记录空值计数。讨论引入了“effective nullability”概念，即字段是否真正非空取决于从根到该字段路径上所有祖先的可空性，而非仅字段自身的 required 标记。

@Anoop Johnson: 提出 effective nullability 概念：只有当字段自身为 required 且所有祖先 struct 均为 required 时才真正非空，否则应记录 null_value_count。

@Xiening Dai: 支持 effective nullability 定义，主张更新规范措辞并移除 'optional null_value_count' 注释，writer 应尽可能为所有嵌套字段记录空值计数。

@Eduard Tudenhöfner: 认为在 optional 父级内的 required 字段包含 null_value_count 是合理的，并在其 content stats evaluator 开发中遇到了相同问题。

初步达成共识：应更新 Iceberg 规范以明确 effective nullability 概念，移除对 null_value_count 仅适用于 optional 字段的限制，并推动相关 PR（如 #17609 和 #17560）落地。下一步是完善规范措辞并统一相关实现。

@Varun Lakhyani: 确认在 FileReader API 层集成的共识，将先实现 Parquet 支持，并同步调研 ORC 的受益方式。

Questions on Read Restrictions implementation

2 条回复 · 2 位参与者

讨论围绕 Iceberg Read Restrictions 提案的实现问题展开，核心是信任关系如何在规范之外落地，以及现有细粒度访问控制策略如何映射到 Read Restrictions。Prashant Singh 指引 Corey Sunwold 参考既有同步会议视频和邮件线程，并解释社区共识与后续计划。

@Corey Sunwold: 信任关系虽不在规范范围内，但对实际实现至关重要；现有凭证模型在 Read Restrictions 下会被打破，需要机制确保引擎正确保护凭证并限制返回内容。

@Prashant Singh: 社区共识是不在规范中定义信任机制，因其高度依赖平台（如 mTLS、OAuth On-behalf、AWS STS 等）；规范只要求客户端确保安全，具体实现由客户端决定。

@Prashant Singh: 计划后续引入 Iceberg SQL UDF 支持；当前 Read Restrictions 已覆盖较多现有场景（如 Ranger、BigQuery），但无法 100% 转换所有策略，不可转换时可拒绝请求。

信任机制由实现方自行解决，不纳入规范；不可转换的访问控制策略可安全失败（如返回 403），后续将通过 SQL UDF 扩展语义支持。
