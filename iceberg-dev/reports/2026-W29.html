Deprecate Equality Deletes in Iceberg V4

14 条回复 · 11 位参与者

本次讨论主要关于在 Iceberg V4 中废弃 Equality Deletes（等值删除），社区普遍支持禁止在 V4 表中写入新的等值删除，转而使用 Deletion Vectors (DVs)。参与者认为等值删除将高昂的连接成本推给了读取端，而 DVs 通过一次性解析位置能显著降低后续读取成本，且 Flink 的索引实践已证明替代方案可行。

@huaxin gao: 等值删除将成本分摊到每次读取，而 DVs 仅需一次性解析；后台转换和索引机制可确保写入路径的低成本，同时解决 CDC 和行级血缘等阻塞问题。

@Ryan Blue: 强烈支持废弃提议，认为这是将维护责任正确转移给写入者的举措；建议 V4 仅禁止写入新的等值删除，现有表升级时可保留旧数据以实现平滑过渡。

@Daniel Weeks: 虽然承认等值删除在写入成本上的优势，但认为其互操作性差、维护复杂且统计信息质量低，目前对生态的负面影响已超过其带来的便利。

初步结论是社区一致同意在 V4 规范中禁止写入新的等值删除，但允许 V3 表升级后保留并读取旧的等值删除文件，无需强制同步重写。下一步将完善 Flink 等引擎的索引与 DV 写入实现，作为替代方案的落地保障。

Should incremental (append) scan semantics be part of the spec?

3 条回复 · 3 位参与者

讨论主要关于是否应将增量扫描语义（特别是增量追加扫描）纳入 Iceberg 表规范。目前各语言实现均依赖 Java 的参考实现，缺乏正式规范导致约定俗成的规则较为脆弱，且 REST 扫描规划 API 已涉及此功能。

@Alexander Bailey: 当前规范对增量扫描定义缺失，导致多语言实现只能盲目跟随 Java 代码，缺乏标准契约，建议参考现有的“时间旅行”读语义进行标准化。

@Xiening Dai: 当前的增量扫描 API 仅返回文件集，只支持追加场景；若要支持包含删除和更新的完整快照差异扫描，需要从 API 层面进行更深入的讨论。

@Ryan Blue: 社区计划在 v4 版本中加强变更检测的要求，从而在规范层面支持所有类型的增量扫描，不再依赖特定实现的惯例。

初步结论是社区已意识到该需求，并计划通过 v4 版本的规范更新来解决，支持更全面的增量扫描语义。

[PR#16827 Review Request] Hilbert Curve Clustering for rewrite_data_files: Better Data Skipping than Z-order

3 条回复 · 2 位参与者

本次讨论主要关于在 rewrite_data_files 操作中引入 Hilbert 曲线排序策略，作为现有 Z-order 的替代方案以优化多列过滤查询的数据跳过能力。作者通过理论分析和 TPC-H 基准测试证明，Hilbert 曲线在扫描文件数量上比 Z-order 减少约 31%，尽管重写时间略有增加，但整体效果积极。社区反馈积极，认为该方案值得推进。

@Gianluca Graziadei: Hilbert 曲线相比 Z-order 能避免空间跳跃，提供更紧密的空间聚类，从而减少查询扫描的文件数量；实现上复用了现有的 Z-order 基础设施，且测试表明扫描文件数减少 31.25%。

@Tanmay Rauth: 肯定了复用 Z-order 编码的实现思路，但建议提供端到端的对比数据（如扫描文件数、重写时间），以更直观地展示 Hilbert 在数据跳过方面的实际收益。

Proposal: File-Level Access Delegation in the Iceberg REST Catalog Spec

0 条回复 · 1 位参与者

讨论围绕 Iceberg REST Catalog 规范中的文件级访问委托模式展开，重点分析了远程签名与预签名 URL 的可行性。作者指出远程签名在跨云实施中面临 TTL 时效限制和 Azure 原生不支持的双重挑战，相比之下预签名 URL 在三大云服务商中支持更为统一。

@William Hyun: AWS 和 GCS 的远程签名存在严格的 15 分钟 TTL 限制，且 Azure 不支持通过 Header 进行远程签名，需依赖不推荐的账户主密钥方案。

@William Hyun: 预签名 URL（Pre-signed URLs）在 AWS、GCS 和 Azure 三大云服务商中均得到了原生且统一的支持，是更优的跨云解决方案。

初步结论倾向于在跨云场景下优先采用预签名 URL 模式，以规避远程签名在 Azure 上的兼容性缺陷及安全风险。

@社区共识: 分开设计避免了无法填充 base file 的 field_ids 列表、难以识别基础文件以及无法轻易删除基础文件等问题。

Add a file data type to Iceberg (v4)

0 条回复 · 1 位参与者

随着 Parquet FILE 逻辑类型的合并，Nitya Kumar Sharma 提议在 Iceberg 中引入相应的文件数据类型（File Data Type），并提交了一份仅关注类型语义（如序列化、统计信息等）而暂不涉及凭证分发的设计文档。该提案旨在独立于访问控制层推进讨论，以便更快就类型系统达成共识，并明确表示这并非对现有提案的反驳，而是希望与其互补融合。

@Nitya Kumar Sharma: 文件类型应定义为一种“命名结构体（named struct）”，包含 uri、offset 等六个固定字段，并遵循 v4 相对路径解析规则。

@Nitya Kumar Sharma: 提案仅支持内联和外部 URI 两种形式，暂不采纳 Parquet #585 允许的同文件内自引用形式，以保持类型的简洁性。

@Nitya Kumar Sharma: 文档范围刻意聚焦于类型层面的语义，将目录代理的凭证分发机制留待上层处理，以便独立推进类型设计。

该提案已启动针对文件类型语义的社区讨论，下一步计划是与现有的凭证分发提案进行协作，共同确定最终的技术方向。
