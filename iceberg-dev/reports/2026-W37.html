Reducing per-row position delete index probes in the vectorized read path

4 条回复 · 2 位参与者

该讨论围绕优化 Spark 向量化读取路径中 position delete 索引的逐行查询开销展开。作者 전대홍 提出在 PositionDeleteIndex 中新增 forEachInRange 默认方法，将连续行号范围一次性传入，避免每行重复解析 Roaring 容器，从而显著降低删除检查 CPU 消耗。Péter Váry 建议考虑 BatchIterator 方案，作者随后进行了实现和基准测试，但结果显示当前 PR 方案更优。

@전대홍: 提出为 PositionDeleteIndex 增加 forEachInRange 默认方法，使 BitmapPositionDeleteIndex 可按范围批量处理删除位置，减少重复的容器查找和边界检查；基准测试显示删除检查 CPU 降低 2.6-9.3 倍，窄投影端到端提升约 13-29%。

@Péter Váry: 建议参考 RoaringBatchIterator 的思路，考虑使用类似 PositionBatchIterator 的批量迭代器来实现该优化。

@전대홍: 对 BatchIterator 方案进行了 JMH 基准测试，结果显示其性能略低于当前 PR 的 forEachInRange 实现，原因是需要二次遍历缓冲区且无法高效跳过无删除的连续区间；因此倾向于保留当前基于默认方法的方案。

初步结论是当前基于 forEachInRange 默认方法的实现性能优于 BatchIterator 方案，且 API 侵入性更小。下一步是继续推进 PR #18027 的社区评审，重点确认在 PositionDeleteIndex 接口中新增默认方法是否为合适的扩展方式。

@Neelesh Salian: 对 RustFS 表示谨慎支持，提醒关注此前社区提出的 CVE 安全问题，强调需要长期支持和及时的安全补丁。

Views with Multiple Representations

3 条回复 · 4 位参与者

讨论围绕 Iceberg 视图中多方言表示（Multiple Representations）的创建与更新工作流展开，重点是如何在不引入自动翻译或规范变更的前提下，让不同引擎（如 Flink、Spark）能安全、便捷地添加或更新自己的 SQL 表示。社区倾向于通过现有 SQL 语法（如 ALTER VIEW 和 CREATE OR REPLACE VIEW）明确区分“更新本引擎表示”与“完全重定义视图”的语义。

@Talat Uyarer: 提出基于现有语法的 SQL 工作流：ALTER VIEW 用于添加/更新当前引擎的表示并保留其他表示，CREATE OR REPLACE 则仅保留当前引擎表示，无需新规范或属性。

@Daniel Weeks: 强调 Iceberg 视图仅解决多方言元数据暴露问题，不负责自动翻译或语义一致性；表示间协调与正确性验证应由用户或创建工具负责。

@Alex Stephen: 支持扩展 ALTER VIEW 作为跨引擎定义视图的便捷方式，并认为在缺乏通用翻译层的情况下，由用户确保各表示一致性是合理选择。

初步共识是 Iceberg 不承担视图表示的自动翻译或一致性保证，推荐通过 ALTER VIEW 等现有语法支持引擎原生更新自身表示，具体工作流和语法语义可进一步细化。

Row-granular concurrency for V3 deletion vectors

3 条回复 · 3 位参与者

讨论围绕 Iceberg V3 deletion vectors 的并发冲突检测从文件级细化到行级（position 级）展开，旨在减少 UPDATE/MERGE 操作在修改同一数据文件但不相交行时的虚假冲突和无效重试。EJ Song 提出在 validateAddedDVs 中通过位图重叠检测合并并发 DV，并给出设计文档；Xiening Dai 和 huaxin gao 均支持该方向，但在实现路径和配置开关上提出不同建议。

@EJ Song: 提议将 validateAddedDVs 的冲突检测从文件粒度细化到 position 粒度，对不相交的并发 DV 进行合并，以减少虚假冲突；倾向在 validation 路径中直接合并，而非引入额外重试循环。

@Xiening Dai: 支持更细粒度冲突解析以提升提交性能，但认为应通过重试提交直到解决真实冲突或失败。

@huaxin gao: 支持方向但指出会增加 driver 端提交时 I/O，建议用表属性开关控制；倾向在 validation 路径合并，并列举了相关已有实现和讨论。

社区初步认可将 V3 DV 并发冲突检测细化到行级的方向；下一步是继续讨论实现路径（validation 合并 vs 重试合并）、是否需要表属性开关，并参考已有 pure-delete 合并实现推进设计。

Defining gc.enabled semantics across engines and clients

2 条回复 · 3 位参与者

讨论围绕 Iceberg 中 `gc.enabled` 属性语义未明确定义的问题展开，起因是一个放宽该属性以支持仅元数据快照过期的 PR。Alexander Bailey 指出该属性未在规范中定义，且在不同实现中存在多种不一致行为；Russell Spitzer 认为核心不变量是“不得删除表的数据文件”，现有行为基本合理；Daniel Weeks 则主张该属性属于历史约定而非规范，不建议将其固化到规范中。

@Alexander Bailey: `gc.enabled` 缺乏统一定义，在 Java 实现和不同客户端中语义不一致，建议社区先在邮件列表中明确其语义再推进相关行为变更。

@Russell Spitzer: 该属性的核心含义是防止 Iceberg 维护操作删除外部系统拥有的数据文件，只要保证不删除数据文件，具体实现方式可以不同。

@Daniel Weeks: `gc.enabled` 更像历史约定而非规范，不建议将其写入规范固化，更应由 catalog 实现在必要时强制执行限制。

初步共识倾向保留 `gc.enabled` 的核心语义，即禁止删除表的数据文件；但对其是否应写入规范尚未达成一致，后续可能需要继续讨论是否将其补充到规范附录或维持现状。

Recommend a standard User-Agent format for REST clients

1 条回复 · 2 位参与者

社区讨论为 Iceberg REST 客户端推荐统一的 User-Agent 格式，以便客户端以一致、可解析的方式向 catalog 标识自身。当前各语言客户端的 User-Agent 格式不一致，导致下游项目（如 Polaris）难以可靠解析客户端信息。该提案获得了多位社区成员的支持。

@rahul mahadev: 提出为 REST catalog 客户端推荐标准 User-Agent 格式，解决当前各客户端（iceberg-java、pyiceberg、iceberg-rust、iceberg-go 等）格式不一致的问题。

@Alex Dutra: 在 Polaris 中尝试通过 User-Agent 和 X-Client-Version 识别客户端时发现复杂且不可靠，认为标准化提案将使该需求变得可行。

@Yufei Gu: 指出下游项目因缺乏标准化而难以构建合适的解析器，以 Polaris PR #4236 为例，支持该提案。

提案获得社区广泛支持（多位成员 +1），Daniel Weeks 对规范提出了少量小意见。下一步预计是根据反馈完善规范并推进落地。
