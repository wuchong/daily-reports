@Ryan Blue: 确认若分发第三方代码，必须在 LICENSE 和 NOTICE 中完整反映；对 THIRD-PARTY-LICENSES 持开放态度，但强调必须有包含法定通知的 NOTICE 文件。

@Kevin Liu: 指出这是创建 Python binding 时的疏漏，应在再次发布 pyiceberg-core 前修复；需先确认 wheel 中打包了哪些库，再补充 LICENSE/NOTICE，且已有 cargo deny 检查许可证兼容性。

Defining gc.enabled semantics across engines and clients

0 条回复 · 1 位参与者

讨论围绕 Iceberg 中 gc.enabled 属性在不同引擎和客户端间的语义与执行方式展开。Alexander Bailey 提议先推进一个较窄的改动：当 gc.enabled=false 时，仅允许以 CleanupLevel.NONE 执行快照过期，不删除底层文件；Dan 和 Russell 则更关注该属性的历史约定性质及是否应正式规范化。

@Alexander Bailey: 建议暂时搁置对 gc.enabled 的正式规范讨论，先推进 PR #17791 的有限改动，即在 gc.enabled=false 时允许仅移除快照记录但不删除文件。

@Daniel Weeks: 认为 gc.enabled 更像历史约定而非规范，不建议在客户端层面强制编码该行为，而应由 catalog 实现在必要时强制执行删除限制。

@Russell Spitzer: 指出该属性最初用于表示 Iceberg 表仅管理元数据、而数据文件由外部系统拥有的场景。

初步方向是将 PR #17791 限定为允许无文件清理的快照过期，以保留现有数据和共享元数据保护；更广泛的 gc.enabled 语义定义和执行机制将另行讨论。
