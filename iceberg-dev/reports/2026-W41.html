Iceberg v4 Stats Tightness

4 条回复 · 5 位参与者

社区讨论了 Iceberg v4 中统计信息边界是否为 tight 的元数据应按列还是按文件/条目标记。经过对使用场景的分析，参与者普遍认为按列标记收益有限且复杂，倾向用文件级布尔标记简化写入与读取。目前讨论已基本收敛到文件级 tightness flag。

@Russell Spitzer: 分析了按列标记 tightness 的多个场景，认为 DV writer 修复统计和恢复统计等关键需求都可以由文件级 flag 覆盖，按列标记会带来不必要复杂性。

@Hongyue Zhang: tightness 的变化主要来自文件级状态（如后续 DV 删除），而变长列截断属于静态列属性；因此建议将 tightness 布尔值从按列移到 v4 tracked_file 条目级，并说明旧表升级时可保持轻量、不重写 manifest。

@Anoop Johnson: 总结社区正收敛到文件级 tightness flag；现有 v3 manifest 中的文件没有该 flag 时默认视为 wide，v4 后新文件可根据是否附带 DV 设置为 true 或 false。

初步结论是采用文件级/条目级 tightness flag 而非按列标记；下一步是在 v4 设计中落实该标记，并明确升级语义：旧条目无 tightness 时按 wide 处理，新文件无 DV 时为 tight，有 DV 时为 wide。

REST spec: expected server behavior when X-Iceberg-Access-Delegation cannot be satisfied

4 条回复 · 4 位参与者

讨论围绕 REST 规范中 X-Iceberg-Access-Delegation 头在服务器无法满足客户端请求的委托访问机制时的预期行为展开。社区倾向于新增 none 值，用于表示客户端不需要 catalog 提供委托访问；对是否明确写入服务器可失败，最终倾向认为无需额外说明。

@Daniel Weeks: 建议用 none 替代 local，表示客户端不请求或不需要 catalog 提供凭据/访问；并认为服务器本来就可以拒绝请求，无需在规范中特别澄清失败行为。

@Yufei Gu: 支持 none，并关注客户端请求机制 A 但服务器返回机制 B 的问题；建议规范允许服务器在请求机制中选择任一或无机制，或使请求失败。

@Youngrae Kim: 总结讨论并推动落地，最初提议同时添加 none 和澄清失败行为，后续根据反馈可只提交添加 none 的规范 PR。

初步结论是在 X-Iceberg-Access-Delegation 中增加 none 值；下一步由 Youngrae Kim 提交规范 PR，且大概率只包含 none，不额外规定服务器失败行为。

Spec clarification: readers must accept promotable types in any data file

0 条回复 · 1 位参与者

讨论围绕 Iceberg 规范澄清展开：当数据文件中的列类型窄于表 schema 中字段类型时，读取器应如何处理。提案指出由于类型提升可能不会在元数据中留下明确标记，读取器必须能够接受可提升的窄类型，而不是仅做精确类型匹配。目前已提交 PR #18404，建议在 Schema Evolution 部分增加明确说明。

@Sandeep Gottimukkala: 类型提升允许字段类型演进而不重写数据文件，因此旧数据文件仍可能保存较窄类型，读取器必须按当前表 schema 类型正确读取。

@Sandeep Gottimukkala: 现有系统中有实现只检查精确类型匹配，未接受所有允许的提升类型，因此需要在规范中明确读取器行为。

@Sandeep Gottimukkala: 建议在规范中新增一句：读取器必须接受字段类型本身，或接受可根据当前格式版本规则提升到字段类型的数据文件列类型，无论字段类型是否发生过演进。

目前处于提案和征求意见阶段，尚未形成最终结论；下一步是通过邮件列表和 PR #18404 收集社区反馈并推进规范文本修改。
