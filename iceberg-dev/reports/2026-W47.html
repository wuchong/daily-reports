Cross-engine determinism for functions in stored expressions

17 条回复 · 9 位参与者

社区讨论存储表达式中函数在不同引擎间重算时的确定性问题，重点涉及检查约束、派生列和 stats-only 字段。多数参与者认为仅靠现有 deterministic 标志不足，建议引入更明确的语义分类，并对需要跨引擎重算的关键场景采用严格定义的函数。讨论已从是否允许 UDF 转向如何划分关键特性、优化特性和一次性计算值的可靠性要求。

@Péter Váry: 建议增加 VOLATILE、STABLE、IMMUTABLE 的 volatility 枚举，以替代或补充现有 deterministic 布尔标志，从而更清晰地区分不同确定性保证。

@Matt Butrovich: 不同引擎对函数语义可能存在差异，难以保证 UDF 在所有引擎中返回相同结果；因此检查约束、索引键和 stats-only 等关键场景应优先使用 Iceberg 规范中明确定义语义和测试向量的函数。

@Andrei Tserakhau: 未知值应按 VOLATILE 处理；stats-only 等优化类字段可以允许非规范函数，但应记录实现来源，引擎无法理解时可忽略并回退到扫描。

初步方向是将特性分为必须跨引擎可重算的关键场景和可忽略或一次计算后存储的场景；关键场景倾向仅允许规范函数，UDF 可保留给默认值等一次性计算存储值。下一步是继续明确函数语义、命名空间或实现标识机制，并更新约束、派生列等相关规范。

DISCUSS] Resolving compaction conflicts with concurrent deletion vectors

10 条回复 · 7 位参与者

社区讨论 Iceberg 中并发删除向量导致 compaction 提交失败的问题。Shawn Chang 提议记录行位置映射，并在提交时将并发删除向量转换到 compaction 输出文件，以避免重写任务失败和重试。该方向获得多位参与者支持，当前进展倾向于先推进不修改规范的内存映射方案。

@Shawn Chang: 提出基于可交换 compaction 的思路，在 rewrite 中记录行位置移动，提交时转换并发提交的删除向量；已有 Spark 实现，希望先聚焦不改规范的内存方案。

@Anurag Mantripragada: 认可方向，认为先不修改规范解决 compaction 提交失败是合理第一步，但设计文档需要补充 API、引擎范围、版本兼容、失败回退等细节。

@Grant Nicholas: 指出 v4 废弃 equality deletes 可能削弱低延迟删除/更新负载与 compaction 的并发兼容性，支持在完全废弃前引入持久化 compaction maps。

初步共识是分阶段推进：先实现内存 compaction map 以解决 compaction 侧冲突，后续再讨论持久化 map 和规范演进；Shawn 将根据反馈修订设计文档并继续征集意见。

Vector Type and Int8 Float16

9 条回复 · 8 位参与者

讨论围绕 Iceberg v4 的 vector(E, D) 类型是否支持 float16 和 int8 元素类型展开，重点比较物理存储、性能和类型校验三类收益。社区总体倾向 Option 3，即在 vector 元素类型中加入 float16/int8，而不是新增通用 Iceberg 原始类型或仅作为存储编码。若相关细节阻碍 v4 完成，也可先发布 int/long/float/double，将窄类型推迟到 V5。

@Russell Spitzer: 提出存储、性能、验证三类动机，并强调当前重点是完成 V4；如果无法尽快形成共识，建议将 float16/int8 推迟到 V5。

@Andrei Tserakhau: 反对把 float16 仅作为 float 的存储编码，支持将 float16/int8 作为独立 vector 元素类型，并要求支持父类型回退、禁止写入端隐式窄化、保持元素类型集合可扩展。

@Péter Váry: 指出 float16 在 Parquet BYTE_STREAM_SPLIT 等场景下仍有约 10% 存储收益，且 AI/ML 生态已有较多窄类型支持，因此倾向 Option 3，但需明确规范与回退行为。

初步结论是采用 Option 3：在 v4 vector 中引入 float16/int8 元素类型，但不作为通用 Iceberg 原始类型。Yan Yan 已根据 11/19 vector sync 会议共识更新 spec PR，下一步是继续评审并在无重大反馈后尽快启动投票。

Should V4 stop writing ORC and Avro data files?

8 条回复 · 8 位参与者

社区讨论 Iceberg V4 是否停止写入 ORC 和 Avro 数据文件，核心关注在保持多格式支持与降低维护成本之间取得平衡。多数意见认为应继续支持至少两种数据文件格式，并优先处理现有格式而非引入新格式。目前讨论已收敛到 V4 停止 ORC 写入但保留读取、暂保留 Avro 写入支持。

@Ryan Blue: 支持 V4 停止写入 ORC，因其功能差距长期存在；同时保留 Avro 作为第二格式，避免只剩单一格式。

@Kevin Liu: 总结社区共识：V4 禁止新 ORC 文件写入、已有 ORC 可读且无需重写，保留 Avro 写入，新格式另议，并发起投票。

@Gábor Kaszab: 澄清提案仅移除 ORC 写支持，升级后现有 ORC 文件仍可读；并提出 V4 中 ORC 基文件上叠加 Parquet column files 的兼容性问题。

初步结论是 V4 停止写入 ORC 数据文件，但保留对既有 ORC 文件的读取支持；Avro 写入支持暂保留以维持至少两种格式。下一步为进行正式投票，并补充迁移文档、讨论新格式准入标准和 column file 跨格式细节。

Name mapping for data files that carry only some field IDs

7 条回复 · 4 位参与者

讨论围绕数据文件仅携带部分 field ID 时，Iceberg 应使用 name mapping 还是 field ID 解析列。社区总体倾向 per-file 规则：文件只要包含任意 field ID 就按 ID 解析，缺失 ID 的字段视为缺失或 NULL；但验证显示各实现对嵌套 list/map 等场景行为不一致，因此推动规范澄清和实现验证。

@Ryan Blue: 文件中缺失 field ID 的列应被视为 NULL。

@Sylwester Lachiewicz: 四个读取器对部分 field ID 文件的处理结果不一致，建议规范明确基于文件 schema 判断，并将缺失 ID 的嵌套 list/map 整体读为 NULL。

@Daksh Dave: 提交 Java Parquet reader POC 验证 per-file 方案，并请求确认 required 容器及未支持嵌套场景应沿用默认值/NULL，还是允许读取失败。

初步方向是采用 per-file 规则，并通过 PR #19037 修订规范、用 PR #19073 提供实现验证；但 Russell 认为该场景类似破损文件，不宜过度细化，后续需围绕真实场景和现有行为继续确认。

社区讨论 Iceberg Spark 多版本支持是否采用共享源码布局，以替代当前按 Spark 版本复制源码的方式。Anurag 通过无 shim 的 POC 评估后发现，共享源码可减少手工 backport，但也会因旧版本 API 限制新功能开发。讨论同时涉及 shim 的治理成本与 Spark 小版本 API 变化带来的风险。

@Anurag Mantripragada: 提出无 shim 的共享源码 POC，认为其能减少 backport，但依赖成本较高，且 AI 使复制和 backport 更容易，因此建议暂不推进。

@Alex Cruise: 认为 shim 虽然烦琐，但比大量复制源码更不易出错，倾向采用大公共代码加薄 shim 的策略，并可根据兼容时代或文件特性调整。

社区同步会初步决定暂时保留按版本复制源码的布局，不合并共享源码 POC；#19025 可保留供后续审阅，若未来新增 Spark 版本造成严重 review 或维护负担，再重新评估。
