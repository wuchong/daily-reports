Proposal: Parquet footer size in Iceberg metadata

2 条回复 · 2 位参与者

Varun Lakhyani 提议优化 Iceberg 小文件（<= 1MB）的读取性能，通过一次性读取整个文件将 GET 请求次数从 3 次减少至 1 次。该方案已在 PR 中实现，并在 JMH 基准测试中取得了约 66% 的性能提升。此外，作者建议参考 arrow-rs 在 parquet-mr 中引入 footer size hint，以寻求更优的实现方式。

@Varun Lakhyani: 针对小文件读取，建议将原本分离的 footer 和数据读取合并为一次全文件缓冲读取，大幅减少 GET 请求。

@Varun Lakhyani: 初步测试显示该优化效果显著，处理 1000 个文件的时间从 537 秒降至 169 秒。

@Varun Lakhyani: 建议在 parquet-mr 层面暴露 footer size hint，以便采用更简洁的实现方式。

已提交初步实现的 PR #16729，目前正寻求社区对优化方案及 parquet-mr 相关改动的反馈。

@Varun Lakhyani: 建议对小文件采用单次 GET 请求获取全量数据，替代现有的串行请求模式（Footer 发现、Footer 获取、数据获取），从而降低延迟。

@Russell Spitzer: 认为该优化对减少 V4 延迟和串行请求瓶颈非常关键，倾向于 Iceberg 优先的解决方案，但也建议 Parquet Java 借鉴 Rust/C++ 实现增加新 API。

@Daniel Weeks: 认为这是值得投入的 IO 性能优化领域，但需考虑 FileIO 层的加密和指标处理，不应仅局限于 Parquet 视角。

@Sung Yun: 当前策略管理依赖列名，导致列重命名时策略重定向，且策略提交无法与模式变更保持原子性，建议通过服务端绑定字段 ID 来解决。

@Christian Thiel: 对提案感兴趣，建议明确名称到字段 ID 的绑定时机，特别是如何处理列的删除与重新添加（drop+re-add）场景。

@Daniel Weeks: 最初对写入端策略执行的必要性提出质疑（认为写入者通常拥有最高权限），后理解这是指策略的生命周期管理而非执行。

已形成初步分析文档，下一步由社区成员审阅文档并提供反馈。
