Integrate EagerInputFile into the manifest reader

10 条回复 · 4 位参与者

社区讨论将 EagerInputFile 集成到 manifest 读取路径，核心是通过预取/一次性读取小文件来加速 v4 Parquet manifest 读取，基准测试显示约 25%-55% 的读取延迟降低。讨论焦点在于集成方式：是仅在 manifest/Parquet 读取路径做定向优化，还是将其下沉为通用 FileIO 层能力。

@Varun Lakhyani: 提出在 ManifestFiles 读取路径默认启用 EagerInputFile，基准测试显示 Parquet manifest 读取可提升约 25%-55%；Avro 基准结果基本中性，并询问社区倾向全局 FileIO 改造还是先做局部接入。

@Daniel Weeks: 建议不要只在 metadata 路径做特殊短路，而应将 eager loading 集成到现有 FileIO 实现中，使任何 InputFile::newStream 都能受益，并通过阈值控制 eager fetch 与标准/vectored IO 的切换。

@Russell Spitzer: 认为该优化对 Parquet 更有意义，对 Avro 不一定必要；倾向更保守地先在 Parquet 读取层（如 Parquet.java）接入，避免把文件格式相关的性能优化复杂化到 FileIO 层。

目前尚未形成最终结论；下一步是继续评估集成层级，可能的方向包括先做 manifest/Parquet 读取路径的保守接入，或推进更通用的 EagerFileIO/FileIO 层 eager loading 实现，并结合基准测试决定默认启用策略。

Read Restrictions: overlapping column projections on nested types

8 条回复 · 6 位参与者

讨论围绕 Iceberg Read Restrictions 规范中嵌套类型字段（struct/list/map）上出现重叠列投影时的客户端处理策略展开，核心争议是禁止重叠并在读取端失败关闭（选项 A），还是定义优先级语义允许重叠（选项 B）。多数参与者基于行业实践分歧、安全性和实现复杂性倾向于选项 A，但 Daniel Weeks 对“未来放宽仍向后兼容”的说法提出异议，认为行为兼容性需要谨慎对待。

@Prashant Singh: 提出嵌套字段投影重叠的问题，并说明当前规范 PR 倾向于选项 A：禁止同一 ReadRestrictions 中容器字段与其嵌套子字段同时被投影，读取端收到此类响应必须使查询失败。

@Sung Yun: 认为业界对嵌套类型策略处理存在明显分歧，不宜仓促定义冲突解决标准；支持选项 A 以先推进 ReadRestrictions，并后续在 8/18 sync 继续讨论新能力引入的成本。

@Daniel Weeks: 反对将“未来放宽禁止规则”视为完全向后兼容，强调这会破坏依赖规范校验的旧客户端行为；主张现在就明确语义，避免协议演进留下互操作性问题。

初步共识偏向选项 A：catalog 不得返回重叠的嵌套列投影，reader 必须 fail closed。后续行动包括在 8/18 sync 上讨论 ReadRestrictions 新能力的兼容性成本，并可能结合行业系统调研进一步确认规范措辞。

[Iceberg v4] null_value_count is only for optional field?

2 条回复 · 2 位参与者

讨论围绕 Iceberg V4 规范中 null_value_count 仅用于 optional 字段的表述是否合理展开。Xiening Dai 指出，若 required 字段的父级 struct 为 optional，则该字段实际可能为 null，因此不能仅凭 required 标记假设非空。Anoop Johnson 提出应以“有效可空性”（字段自身及所有祖先均为 required 才真正非空）来理解，并认为现有实现已正确处理。

@Xiening Dai: required 字段在其父 struct 为 optional 时仍可能为 null，查询引擎不能仅依据 required 标记做优化，应显式记录 null_value_count。

@Anoop Johnson: 字段是否真正非空取决于从根到该字段路径上的有效可空性；只有字段本身及所有祖先 struct 均为 required 时才无需记录 null_value_count，现有统计与评估逻辑已依赖显式 null count。

@Xiening Dai: 认同有效可空性概念，建议更新规范措辞并移除“optional null_value_count”的注释，写入端应尽可能为嵌套字段记录 null count。

初步共识是规范中关于 optional 字段与 null_value_count 的表述需要澄清或修改，建议明确“有效可空性”定义，并鼓励写入端无论字段标记为 required 或 optional，都尽可能记录 null_value_count。

Dedicated sync for Iceberg Index Support

1 条回复 · 2 位参与者

本次 Iceberg 社区同步会议围绕索引支持的元数据设计与索引排序定义展开，重点讨论了是否保留索引快照历史，以及是否用 transform 函数列表来表达索引键排序。会后 Péter Váry 对基于 transform 函数的方案进行了利弊分析，认为其灵活但可能增加引擎实现复杂度；Flavio Junqueira 则进一步质疑该方案相对现有分区、排序和 min-max 统计信息裁剪的增量价值，并询问引擎如何消费索引。

@Péter Váry: 会议同意保留 index snapshot 历史，但不保留其他 index property 历史；如果读取器需要后续可能被修改的信息，应复制到对应 snapshot 中。

@Dan / Yingyi: 提出通过 transform 函数列表定义 index_keys，例如按 day(col3)、truncate(col4, 2) 排序，并用原始列值、文件名和行位置解决确定性排序问题。

@Flavio Junqueira: 质疑在引擎已能利用分区、排序和列统计信息进行裁剪的情况下，secondary index transform 函数的目标价值，并要求澄清引擎如何消费索引及输入到文件的映射位置。

初步共识是保留索引快照历史，并将易变信息复制到快照中；但关于是否采用基于 transform 函数的索引排序定义，以及索引对引擎的实际价值和消费方式，仍需进一步澄清和讨论。
