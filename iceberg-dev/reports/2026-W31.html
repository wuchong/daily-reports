Changing the default append mode for Spark Streaming in Iceberg Java 1.13

8 条回复 · 7 位参与者

讨论主要关于在 Iceberg Java 1.13 版本中，将 Spark Streaming 的默认写入模式从 'fast append' 切换为 'merging append'，以解决因大量小 manifest 文件导致的元数据膨胀和读取性能下降问题。社区成员普遍支持该提议，认为这能改善元数据管理并与其他引擎（如 Flink）保持一致，同时也讨论了切换模式可能带来的延迟抖动风险。

@Amogh Jahagirdar: 提议在 1.13 版本中将 Spark Streaming 默认 append 模式改为 merging append，以避免 fast append 产生大量小 manifest 文件，从而减少对激进维护的依赖。

@Gianluca Graziadei: 担忧 merging append 可能导致周期性的提交延迟尖峰，建议关注 P99 延迟及集群层面的相关性尖峰问题。

@Daniel Weeks: 支持变更，认为无需额外基准测试验证，因为 Flink 和 Kafka Connect 已采用此默认路径且效果良好，且元数据管理更优。

社区达成共识，将在 Iceberg Java 1.13 版本中默认启用 merging append 模式，同时建议 PyIceberg 也进行相应切换。

Spark Shared-source layout for version support

1 条回复 · 2 位参与者

讨论主要探讨了为减少代码维护成本，在 Iceberg Spark 模块中引入类似 Delta Lake 的共享源码布局机制。Anurag 展示了概念验证结果，证明该方案能大幅提高代码复用率，Xin 则基于 Delta 的经验对 shim 层的治理提出了建议。

@Anurag Mantripragada: 当前的 Spark 版本支持模式导致每次升级需复制大量代码，维护成本极高；通过 PoC 验证，共享源码布局可实现约 88% 的代码共享，显著降低新增版本的 PR 复杂度。

@Xin Huang: 共享源码方案前景良好，但需吸取 Delta Lake 的教训，从初期就重视 shim 层的治理，防止其随时间推移变得臃肿。

@Xin Huang: 建议通过引入版本中立的适配器接口、保持业务逻辑与测试套件共享、以及增加 CI 监控等手段，确保 shim 层仅用于 API 适配且长期可控。

初步结论是该方案在技术上可行且优势明显，下一步需重点解决 Gradle 构建和 Spotless 配置等技术细节，并制定 shim 层治理策略以防止代码腐化。
