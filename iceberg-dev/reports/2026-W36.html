Field ID tracking for non-materialized columns in v4

7 条回复 · 4 位参与者

讨论围绕 Iceberg v4 中如何为非物化列（如索引或排序表达式产生的值）分配字段 ID 展开。Ryan Blue 提出通过表达式元数据复用现有字段映射机制，参与者就表达式确定性、数据类型存储及字段引用方式等细节进行了讨论并基本达成共识。

@Ryan Blue: 非物化列的元数据必须完整描述函数行为，仅支持基于单行输入的确定性表达式，不设计依赖隐式分布的函数。

@Gianluca Graziadei: 建议明确区分纯行级确定性表达式与依赖数据分布的表达式（如 Hilbert），并要求表达式参数（含拟合常量）必须内嵌以保证可验证性。

@Péter Váry: 支持该提案简化索引定义，建议显式存储结果数据类型并使用字段 ID 引用以增强健壮性，同时提出可复用排序顺序（Sort Order）概念。

初步达成共识：提案无需重大修改，但需在规范中明确表达式必须为无隐藏输入的确定性函数，且元数据需完整包含所有参数；后续可将排序顺序纳入同一框架考虑。

Views with Multiple Representations

7 条回复 · 6 位参与者

讨论围绕 Iceberg View 规范中“单个视图支持多个引擎方言表示”在实践中的可操作性展开。Alex Stephen 提出新增 view property `replace.append-dialect.allowed`，以便向已有视图追加新的引擎表示，避免只能依赖 REST API。社区多数意见倾向于不引入属性开关，而是通过 `ALTER VIEW` 语义来更新或追加当前引擎自身的表示，并保留其他引擎已有表示。

@Alex Stephen: 当前 View 规范虽支持多方言表示，但缺少追加表示的能力，用户只能替换或直接调用 REST API；提议通过新属性允许向已有视图追加新的方言表示。

@Daniel Weeks: 应通过 `ALTER VIEW` 更新或添加当前引擎自身的表示，而不是让引擎处理其他引擎的 SQL；反对用属性开关改变行为，因为会引入配置副作用。

@Talat Uyarer: 提出较完整的 SQL 工作流：`CREATE VIEW` 创建本引擎表示，`DESCRIBE EXTENDED VIEW` 展示所有方言文本，`ALTER VIEW ... AS` 追加/更新当前引擎表示并保留其他表示，`CREATE OR REPLACE VIEW` 则重置为当前引擎表示。

初步共识是不通过新增属性开关解决该问题，而更倾向利用现有或扩展的 `ALTER VIEW` 语义实现“追加/更新当前引擎方言并保留其他表示”。下一步需要进一步明确 SQL 工作流、引擎展示多方言 SQL 的方式，以及读取时缺少匹配方言应快速失败而非静默回退。

Recommend a standard User-Agent format for REST clients

6 条回复 · 7 位参与者

Rahul Mahadev 提议为 Iceberg REST catalog 客户端制定统一的 User-Agent 格式，以解决当前各语言客户端标识不一致、X-Client-Version 含义不统一的问题。提案建议采用 RFC 7231 标准的 product/version token 格式，并强调该头部仅用于可观测性，不作为认证或能力协商依据。社区多位成员表示支持，认为标准化将显著改善 catalog 侧的客户端识别、调试和运维。

@rahul mahadev: 提出统一 User-Agent 格式：按 engine -> integration -> Iceberg library -> runtime 顺序排列 token，Iceberg library token 必须存在；并提交 draft PR #17727，同时列出 X-Client-Version 处理、命名统一、环境标识等开放问题。

@Alex Dutra: 支持提案，指出此前在 Polaris 中通过 User-Agent 和 X-Client-Version 识别客户端非常复杂且不可靠，标准化后将使客户端识别真正可行。

@Ryan Blue: 认为提案整体良好，表示支持。

社区对提案总体持积极态度，已有多个 +1 支持；下一步是继续完善规范 PR #17727，并在格式确认后推动 Java、Python、Rust、Go 等客户端统一实现该 User-Agent。

File Type: URI Relativization Behavior

4 条回复 · 5 位参与者

讨论围绕 Iceberg File Type 提案中 URI 子字段的处理行为展开，核心议题是 URI 是否允许相对路径、读取时是否应转换为绝对路径、维护操作如何处理文件引用以及所有权归属问题。多数参与者倾向于将 URI 视为数据，Iceberg 应保持原样读写，不进行路径转换或清理。

@Russell Spitzer: 允许相对 URI，读取时应原样返回，维护操作默认不拥有引用路径，所有权机制可后续再定。

@Daniel Weeks: Iceberg 应忠实保留用户提供的值，不做修改；默认不清理文件引用，所有权和权限控制交由 Catalog 处理。

@Shawn Chang: 建议在 File Type 中增加 owned 字段以显式表达生命周期所有权，访问控制仍由 Catalog 负责。

初步共识是 URI 应作为数据原样处理，允许相对路径且默认不进行维护清理；下一步需讨论是否引入所有权字段以及为引擎提供路径解析指导。

Table and Column Label Metadata in Iceberg REST Catalog

讨论围绕在 Iceberg REST Catalog 中引入表和列的标签（labels）元数据展开，核心争议在于标签应复用现有 config 机制还是定义为独立的结构化实体，以及规范应保留多大自由度。多数参与者支持该提案，但强调需明确标签的语义边界和客户端处理预期，避免过早约束实现创新。

@Prashant Singh: 主张先明确定义标签的结构化实体（如是否支持多值），再推进规范落地，反对将标签混入 catalog 控制的 config 中。

@Andrei Tserakhau: 支持保留标签定义的灵活性，认为应将其视为不透明的 catalog 提供元数据，避免在用法未明前过度标准化而限制创新。

@Kevin Liu: 支持提案，认为标签可用于暴露平台级业务元数据（如 Fabric 中的描述信息），并强调实现时应兼顾互操作性。

提案获得初步支持，下一步需在规范中明确标签应为不透明、仅信息性的 K/V 元数据，并澄清其与 config 的界限，同时保留实现灵活性。

_pos column in efficient column updates in Iceberg

2 条回复 · 2 位参与者

讨论围绕 Iceberg 高效列更新中是否应保留 _pos 列展开，核心争议是该列是否应仅为调试目的而存在。多数参与者倾向于移除 _pos 列，认为位置一致性应由写入引擎在写入时保证，而无需在规范中持久化该列。讨论最终趋向于将 _pos 视为写入器责任，而非规范要求。

@Marco Kroll: 认为仅为调试目的保留 _pos 列在 Iceberg 中缺乏先例，倾向于移除；若必须保留，建议设为可选，并明确其不参与读取路径。

@Ryan Blue: 认为 _pos 列有助于检测写入器遗漏已删除行的问题，倾向于保留，但承认当前 Parquet 存储效率不高，因此立场不强硬。

@Russell Spitzer: 主张移除 _pos 列，认为位置不一致问题应在写入时由引擎检测并中断，无需持久化该列。

初步共识是移除 _pos 列，认为位置对齐是写入引擎的责任，无需在 Iceberg 规范中强制要求；后续可将此结论正式写入设计文档。
