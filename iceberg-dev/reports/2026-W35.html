_pos column in efficient column updates in Iceberg

10 条回复 · 7 位参与者

社区讨论 Iceberg 高效列更新（efficient column updates）中是否在列文件里持久化 `_pos` 列。多数参与者认为在 dense 表示和行对齐前提下，持久化 `_pos` 冗余且会增加实现与理解成本，倾向于移除；但 Ryan Blue 提出保留可用于检测写入端遗漏已删除行等不可恢复问题。

@Marco Kroll: dense Null 填充表示已能隐式表达位置，通过行数比较即可验证所有行已写入，因此 `_pos` 的调试和校验作用有限。

@Leonid Lygin: 持久化 `_pos` 会带来规范清晰度和实现分歧问题：文件已对齐时 `_pos` 冗余，且读取端可能出现按位置读取或按 `_pos` 读取两种合法实现。

@Ryan Blue: 概念上需要的是原始数据文件中的行位置；若不存储 `_pos`，写入端遗漏已删除行将是不可检测且不可恢复的问题，因此倾向保留，但并非强烈反对移除。

初步共识倾向不再在列文件中持久化 `_pos`，但尚未最终定案；下一步是在下次 sync 会议继续讨论，并考虑在设计文档中确认该决定。

Flink version support in Iceberg 1.12.0

10 条回复 · 5 位参与者

Iceberg 社区围绕 1.12.0 版本应支持的 Flink 版本矩阵展开讨论，核心议题是采用“LTS + 两个最新 Flink 版本”的支持策略，以及是否在 1.12.0 中保留版本重叠以便用户平滑升级。讨论最终倾向于先支持 Flink 1.20 LTS、2.1、2.2、2.3，并通过已提交的 PR 推进发布。

@Péter Váry: 提议采用“LTS + 两个最新 Flink 版本”策略，认为虽然缺少版本重叠不理想，但跳过升级更糟，并推动尽快完成升级以推进 1.12.0 发布。

@Maximilian Michels: 支持“LTS + 两个最新 Flink 版本”策略，认为跳过某个 Flink 或 Iceberg 版本没有问题，并建议长期探索更轻量的多版本支持方式。

@Talat Uyarer: 认为从生产角度保留版本重叠有意义，建议 1.12.0 支持 Flink 1.20、2.1、2.2、2.3，并从后续版本开始正式执行新策略。

社区已合并支持 Flink 2.2 和 2.3 的 PR（#17849），并决定暂时保留 Flink 2.1 支持，以便用户可独立升级 Flink 与 Iceberg；后续将继续推进 1.12.0 发布，并可能需要 rebase 其他待发布的 Flink 相关 PR。

Table and Column Label Metadata in Iceberg REST Catalog

3 条回复 · 3 位参与者

讨论围绕在 Iceberg REST Catalog 的 load 响应中新增可选、只读、扁平化的 labels 字段展开，目标是暴露 catalog 拥有的对象元数据，同时保持规范最小化和向后兼容。社区基本认同 labels 与 table properties、config 及 Read Restrictions 的边界，但对其在治理、继承和跨 catalog 同步场景下的语义仍有顾虑。

@Andrei Tserakhau: labels 应是 catalog 拥有并在加载时暴露的只读元数据，不定义解释或强制语义，治理、同步和身份问题不属于本提案范围。

@Prashant Singh: 担心治理场景下的附加/继承语义、嵌套字段冲突和跨 catalog 稳定 ID，并质疑为何不复用现有 config 或先设计结构化实体。

@Ryan Blue: 反对把用户可控属性混入 catalog 控制的 config，支持先落地只读 labels 以解决当前通过 table properties 传递标签的问题，无需等待完整结构化方案。

初步共识是推进最小化、只读的 labels 字段作为读取路径标准，后续治理语义、结构化实体和跨系统同步问题可在独立提案中继续讨论。

Proposal: File-Level Access Delegation in the Iceberg REST Catalog Spec

1 条回复 · 2 位参与者

讨论围绕 Iceberg REST Catalog 规范中文件级访问委托（File-Level Access Delegation）展开，重点是如何支持预签名 URL 场景。参与者就两种场景达成一致：场景1（直接返回预签名URL）无需规范变更，场景2（通过 /sign 端点按需签名）需扩展规范并考虑批量签名 API 以解决大表性能问题。

@Prashant Singh: 场景1无需规范变更，已通过 PR #17457 实现通用的 HTTPInputFile/HTTPInputStream；场景2建议引入批量签名 API 以避免逐文件签名导致服务端过载。

@William Hyun: 支持场景1无需规范变更；场景2建议复用 /sign 端点并新增 X-Iceberg-Access-Delegation: pre-signed-urls 头部，同时提议讨论批量签名端点，并表示可提供 POC。

@Daniel Weeks: 认为 Azure 的特殊性使当前远程签名困难，但预签名模型可在现有远程签名 API 框架下实现。

初步共识：场景1无需规范变更，场景2需规范扩展；下一步由 William 提供场景2规范变更的 POC，并推进批量签名 API 的讨论。

Iceberg Rust: moving the DataFusion integration into a separate repository

1 条回复 · 2 位参与者

Iceberg 社区讨论是否将 DataFusion 集成从 iceberg-rust 仓库拆分到独立仓库，以解决开发速度和评审带宽不足的问题。讨论中提出了多种方案，包括拆分仓库、扩大 DataFusion 贡献者在 iceberg-rust 中的评审权限等，核心目标是在提升迭代效率的同时保持与 Iceberg 核心的设计、测试和治理关系。

@Shawn Chang: 总结了社区共识与未决问题：拆分仓库可能提升 DataFusion 集成的迭代速度，但需权衡是否应通过扩大 DataFusion 评审者参与来替代拆分，并关注跨仓库兼容性测试、核心与集成边界划分及 Apache 治理问题。

@Manu Zhang: 支持将 DataFusion 集成和测试迁移到一个 Apache 治理下的独立仓库，并建议将该议题带到社区同步会议讨论。

@Gabriel Musat: 提出折中方案：不拆分仓库，而是授予部分 DataFusion PMC 成员（如 Matt Butrovich 和 Tim Saucer）对 iceberg-datafusion crate 的受限提交权限，通过 CODEOWNERS 文件限制范围，以缓解评审瓶颈。

目前尚未达成最终决定，但社区普遍认可存在评审带宽问题，并倾向于探索既能提升开发效率又能维持与 iceberg-rust 核心紧密协作的方案。下一步可能包括在社区同步会议中进一步讨论，并评估授予 DataFusion 贡献者受限提交权限或仓库拆分的可行性。

storm-iceberg: new Apache Storm module for low-latency processing and Iceberg ingestion

Apache Storm 社区宣布新增外部模块 storm-iceberg，可在 Storm 拓扑内将流式 tuple 直接写入 Iceberg 表，无需经由 Kafka Connect、Flink 或 Spark。该模块已合并至 Storm master 分支，目标随 3.1.0 发布，当前可构建运行。

@Gianluca Graziadei: storm-iceberg 支持仅追加写入，采用 at-least-once 语义，通过目标文件大小与基于 tick tuple 的时间策略双维度控制提交，并利用 WAL 实现重启恢复、清理孤儿文件与重试待提交。

@Gianluca Graziadei: 与现有方案相比，其差异在于更细粒度：映射、过滤和分区路由在拓扑内按 tuple 完成，算子可控制 tuple 落入哪个数据文件。

@Gianluca Graziadei: 发布前希望社区协助提供可信的基准测试方法，并反馈 bug。

模块已合并并计划随 Storm 3.1.0 发布；下一步是寻求外部基准测试和 bug 报告以完善发布。

Read Restrictions: overlapping column projections on nested types

0 条回复 · 1 位参与者

本次讨论围绕 Iceberg 规范中嵌套类型列投影（column projections）出现重叠时的读取限制问题展开。社区最终倾向于明确禁止重叠投影，并由 catalog 侧负责去冲突或直接失败，而不是将复杂处理留给客户端。Prashant Singh 已根据该结论更新了规范 PR。

@Daniel Weeks: 认为不应以“向后兼容、以后可修”为由搁置问题，支持采取更明确立场：由 catalog 处理冲突或禁止重叠。

@Russell Spitzer: 引用此前 default values 讨论中的先例，主张应禁止存在歧义的状态，与本次禁止重叠投影的方向一致。

@Prashant Singh: 总结讨论结论并更新 spec PR，明确在 catalog 侧和客户端预期中都禁止重叠列投影。

初步结论是禁止嵌套类型列投影的重叠行为，由 catalog 负责处理冲突或直接失败；下一步是审阅并推进已更新的 spec PR。
