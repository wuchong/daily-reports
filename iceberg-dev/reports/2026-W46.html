Name mapping for data files that carry only some field IDs

8 条回复 · 7 位参与者

讨论聚焦于 Iceberg 规范中当数据文件仅部分字段携带 field ID 时，name mapping 应按文件整体回退还是按单个字段回退。社区梳理了 Java、PyIceberg、Rust、Go 等实现差异，并追溯规范文本演变，最终倾向维持原有 per-file 语义。

@Sylwester Lachiewicz: 指出规范对部分字段带 field ID 的文件存在按文件与按列两种解读，且各实现不一致，建议统一规范并补充验证用例。

@Russell Spitzer: 追溯历史后认为 name mapping 原意是仅用于完全不含 field ID 的文件，2024 年按列措辞并非有意变更，建议修正规范而非扩展行为。

@Ryan Blue: 反对混合使用 name mapping 与内嵌 field ID，认为文件出现任何 ID 即应按 ID 解析，缺失 ID 的列应读为 null。

初步共识是采用 per-file 规则：只要文件包含任意层级的 field ID，就按 ID 解析并忽略 name mapping；下一步是提交规范 PR 修正措辞，并更新 iceberg-verification 测试，以明确缺失 ID 及嵌套字段的预期行为。

Should V4 stop writing ORC and Avro data files?

3 条回复 · 4 位参与者

讨论围绕 Iceberg V4 是否停止新写 ORC 和 Avro 数据文件展开，重点权衡特性缺口、维护成本与向后兼容性。多数观点认可 Parquet 是当前主要选择，但需保留对既有 ORC/Avro 文件的读取能力，并保持未来写入路径对其他格式的开放性。

@Kevin Liu: 提出 V4 可停止写入 ORC/Avro 数据文件，理由是二者对新特性支持不足且上游格式演进有限，但已有文件仍应可读。

@Maximilian Michels: 支持放弃 ORC/Avro 写支持，认为社区已选择 Parquet；但必须保留读取兼容，并确保写入路径未来仍能扩展到其他格式。

@Zheng Hu: 建议引入文件格式兼容性或能力标志，让表拒绝文件格式不支持的特性，从而将表格式演进与具体文件格式能力解耦。

初步方向是 V4 可能限制或停止 ORC/Avro 的新写入，以 Parquet 为主要写入格式并保留读取兼容；后续需要明确迁移指南、兼容性机制，以及是否引入如 Vortex 等新格式。

Kafka Connect CDC writes without equality deletes

3 条回复 · 4 位参与者

讨论聚焦 Kafka Connect CDC sink 是否通过在提交前将 equality deletes 转换为 deletion vectors，从而避免继续产生新的 equality deletes。当前已有基准测试显示顺序 ID 转换开销较低，但随机 UUID 在大表上扫描代价较高，社区关注其扩展性和并发提交竞争。

@Andrei Tserakhau: 建议由 sink coordinator 在提交前把 equality deletes 转换为 DV，保持 append-only 默认、CDC 可选，并确保 sink 不再提交新的 equality delete。

@Maximilian Michels: 支持消除 equality deletes 的方向，认为实现可暂时引擎特定，但 v4 应尽量复用；同时担心无索引扫描的扩展性和 IO 成本。

@Grant Nicholas: 担心将 equality deletes 改为 DV 后，在删除多、低延迟提交的 Kafka Connect CDC 场景会加剧与 compaction 等写入的提交竞争，需要验证性能影响。

社区总体认可避免新增 equality deletes 的方向，但尚未最终定案；下一步是补充与 compaction 并发提交的竞争测试，并评估索引或更通用转换方案，koodin9 预计 12 月上半月提供测试结果。
