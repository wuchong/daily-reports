Handling of existing statistics files

8 条回复 · 3 位参与者

讨论主要围绕当多个引擎为同一快照写入统计信息时如何处理现有统计文件，核心争议在于是否应支持每个快照关联多个统计文件以及如何处理未知 blob 类型。参与者分析了当前规范允许列表但实现强制替换的现状，并深入探讨了引入文件“所有权”机制或扩展规范以解决冲突的可行性与复杂性。

@Tamás Máté: 认为丢弃未知 blob 比传递更安全，担心多文件会增加规划延迟，主张统计信息应与快照生命周期绑定。

@Gábor Kaszab: 指出当前 Java API 强制替换现有统计信息，质疑在规范中定义统计文件“所有权”的复杂性及其对开源引擎的实际收益。

@dzeri96: 提议支持每个快照多个统计文件并通过新增字段区分，主张规范应保持开放性以支持专有扩展和未来需求（如二级索引）。

目前尚未达成明确共识，虽然技术上发现需要修改 Java API 以支持多文件，但在规范层面如何定义统计文件的所有权及区分机制仍有待进一步讨论和征求更广泛的社区意见。

[Discussion] Collation Support

1 条回复 · 2 位参与者

讨论主要围绕 Iceberg 排序规则支持中 ICU 版本标记层级（列级 vs 文件级）以及边界值存储形式（原始值 vs 排序键）的设计权衡。Alexander 对不同方案在文件剪枝性能和互操作性方面的影响提出疑问，Andrei 则详细阐述了存储原始值在跨版本兼容性上的优势，并解释了文件级版本标记的设计考量。

@Alexander Löser: 列级版本标记能激励引擎统一版本以实现全面剪枝，而文件级标记虽允许版本多样性，但可能导致不同引擎间的剪枝效果“分裂”。

@Andrei Tserakhau: 存储原始值优于排序键，因为原始值允许跨版本重新解释和剪枝，而排序键在不同 ICU 版本间不可比较，前者是后者的功能超集。

@Andrei Tserakhau: 文件级版本标记主要影响剪枝性能而非正确性，设计上允许引擎读取所有数据，但仅对能处理其版本指标的文件进行剪枝。

初步讨论倾向于采用存储原始值结合文件级版本标记的方案，以在保证数据可读性的前提下优化跨引擎的剪枝性能。

QuadTree-inspired physical spatial partitioning for Iceberg

@Seyed Muhammad Mahdi Hoseini: 提议使用受四叉树启发的物理分区代替基于元数据的剪枝或全局排序，以保持空间局部性。

@Seyed Muhammad Mahdi Hoseini: 该方案支持自然增量摄入，无需昂贵的全局重排或大规模 Shuffle 操作，适合持续增长的数据集。

@Seyed Muhammad Mahdi Hoseini: 实现为独立于 Iceberg 和 Parquet 版本的外部框架，实验显示查询性能与空间填充曲线方法相当。
