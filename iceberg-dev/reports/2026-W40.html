Changing avg_value_size_in_bytes to total_bytes in content stats

6 条回复 · 4 位参与者

社区讨论将 Iceberg 内容统计中的 avg_value_size_in_bytes 字段改为 total_bytes，认为记录总字节数比平均值更利于聚合和估算。讨论进一步聚焦在 Java API、JSON 序列化和 REST spec 中如何处理已发布的 avgValueSize 接口。

@Eduard Tudenhöfner: 提议将 avg_value_size_in_bytes 重命名为 total_bytes，因为平均值会增加聚合难度；同时指出 Java 实现中 avgValueSizes() 刚在 1.12.0 发布，直接重命名会带来 API 破坏。

@Daniel Weeks: 确认可以通过 total_bytes 和 value_count 推导平均值，因此 total_bytes 对估算更有价值，因为它提供了明确的大小上界。

@Ryan Blue: 支持使用 total 而非 average，并建议新增 totalBytes，同时让 avgValueSize 作为派生值计算。

初步共识是底层只存储 total_bytes，Java API 可保留 avgValueSize 作为派生值；Steven Wu 进一步建议不在 JSON parser 和 REST spec 中保留派生的 avgValueSize，因为 v4 表尚未在 REST spec 中支持，JSON 序列化的破坏性变更可接受。

Non-overlapping index region files

5 条回复 · 3 位参与者

讨论围绕 Iceberg 索引规范中 region 文件必须全局有序且不重叠的设计取舍展开。Shawn Chang 质疑该约束带来的写放大、维护复杂度和未来演进风险，并建议明确记录替代方案；Péter Váry 解释当前设计是为了保证单键查找快速且可预测。Russell Spitzer 提到此前似乎已倾向于 Ryan 提出的有界 overlay 方案，但讨论仍聚焦于是否先从更简单的非重叠方案开始。

@Shawn Chang: 非重叠约束会导致写放大和维护复杂度，且未来若允许重叠可能成为破坏性变更，因此应明确记录设计权衡，并考虑有界 overlay 等折中方案。

@Péter Váry: 当前设计优先优化快速、可预测的单键查找；非重叠范围可使查找只需读取一个 region 文件，避免多文件读取、合并和延迟不可预测的问题。

@Russell Spitzer: 社区此前似乎已讨论并倾向 Ryan 的有界 region 文件方案，即每个 region 最多由两个文件组成。

初步方向仍是优先采用更简单、非重叠的索引设计以保证读取延迟可预测；后续需要补充设计权衡文档，并在有更多数据后再评估是否引入有界 overlay 或针对 covering index 的优化。

GlueCatalog and what it writes to the Glue table on commit

2 条回复 · 3 位参与者

讨论围绕 Iceberg GlueCatalog 在 commit 时写入 Glue 表的元数据范围展开。Javier 提出当前 Glue 仅写入 table_type、metadata_location 等最小信息，而 Hive Catalog 会同步更多表属性，导致仅读取 Glue 的工具无法获取 Iceberg 表属性，因此询问是否可让 Glue 镜像 HMS 行为。Shawn 和 Daniel 对扩大同步持谨慎态度，认为 Glue 与 HMS 设计定位不同，且外部目录存在元数据不一致风险。

@Javier Sanchez Beltran: GlueCatalog 当前只写入最小元数据，导致治理、发现等只读 Glue 的工具无法直接看到 Iceberg 表属性；建议可选地将表属性、快照摘要、schema 等同步到 Glue，并设置大小上限。

@Shawn Chang: Glue 中最小元数据足迹是有意设计，Glue 主要作为控制平面/目录表示，Iceberg metadata 才是真实来源；不建议简单镜像 HMS 行为。

@Daniel Weeks: HMS 和 Glue 都存在与 Iceberg metadata 的 split-brain 问题，外部工具可能直接修改 catalog 表示导致不一致，因此不应依赖这些同步元数据做安全或治理。

初步倾向是保持 Glue 的最小元数据设计，不建议直接复制 HMS 的完整属性同步；如需支持治理/发现场景，应谨慎评估一致性、大小限制、保留键和删除键等问题。

Iceberg v4 Stats Tightness

2 条回复 · 3 位参与者

讨论围绕 Iceberg v4 中统计信息 tightness 在存在 Deletion Vector（DV）时如何表示的问题展开。Anoop Johnson 提出，当文件附加 DV 后，统计信息通常被视为 non-tight，从而影响基于元数据的查询优化，因此需要一种在 DV 存在下仍能表达 tightness 的方案。Russell Spitzer 和 Daniel Weeks 分析了不同场景后，倾向于采用文件级（file-wide）flag 而非按列标记。

@Anoop Johnson: v4 引入 tightness 概念用于判断上下界是否真实存在于文件有效行中，但 DV 的存在会使统计信息被默认视为 non-tight，需要新的表示方式以保留元数据查询优化能力。

@Russell Spitzer: 分析了按列 tightness 可能适用的几种模式，认为现实场景主要是 DV writer 自行修复边界或通过命令恢复 tight stats，这两种情况都只需要文件级 flag，因此倾向文件级方案。

@Daniel Weeks: 支持 Russell 的分析，认为按列 tightness 的潜在用例较窄或不切实际，建议采用文件级 flag。

初步共识是采用文件级（file-wide）flag 来表示存在 DV 时的统计信息 tightness，而不是引入更复杂的按列标记。下一步可继续在设计文档或邮件列表中完善方案细节。
