Adding X-Iceberg-Client-Capabilities header to REST spec

12 条回复 · 8 位参与者

讨论主要围绕是否在 REST 规范中引入 `X-Iceberg-Client-Capabilities` 标头以支持“读限制”功能。部分开发者认为全局标头会增加复杂性且难以与特定端点行为关联，建议通过引入 `v2 loadTable` 端点来处理前向不兼容的变更。最终讨论倾向于放弃该标头，采用折中方案：在 v1 中允许读限制（由管理员负责信任验证），并在未来的 v2 中强制要求客户端支持。

@Daniel Weeks: 反对全局标头带来的复杂性，认为应通过版本化端点（v2）来明确处理行为变更，而非依赖能力协商。

@Ryan Blue: 提出引入 v2 端点是处理前向不兼容变更的清晰方式，并建议折中：v1 允许读限制，v2 强制执行。

@Russell Spitzer: 指出协议无法强制信任关系，建议在 v1 中直接添加读限制而无需能力标头，v2 工作并行推进。

初步结论是移除 `X-Iceberg-Client-Capabilities` 标头，在 v1 接口中推进读限制功能（依赖管理员进行信任配置），并在未来的 v2 接口中将其作为强制要求。

@Xiening Dai: 现有的单表 LoadTable API 导致多表查询快照不一致，建议新增批量 LoadTables API，利用 Catalog 后端存储（如 DynamoDB）的事务能力提供全局一致性视图。

@Maninder Parmar: 指出 CSN (Catalog Snapshot Number) 提案也能解决原子读取问题，且无需重写存储层的 artifacts，认为该提案与批量加载的思路在目标上是一致的。

@Xiening Dai: 认为两种方案不冲突，核心在于定义跨表快照读取接口；对于当前时间点的快照读，直接利用后端存储的 SI 事务比 CSN 方案更简单直接。

初步结论是两种方案在目标上一致且可互补，Xiening 已在文档中回复具体细节，后续将围绕定义跨表快照读取接口继续推进。
