Column Update File Representation

7 条回复 · 5 位参与者

讨论主要围绕列更新文件应强制采用“密集表示”还是将选择权留给各个引擎实现。多位开发者指出，若不强制规定，实际上会迫使所有读取端支持实现更复杂的稀疏表示，因此共识转向强制使用密集表示以简化读取路径。Anurag 将在下次同步会议上正式确认这一决定。

@Péter Váry: 若规范不明确指定表示方式，实际上要求所有引擎都必须支持稀疏表示，这会增加读取路径的性能开销和复杂性。

@Steven Wu: 支持强制使用密集表示（填充值），认为反对该方案的论据（如统计信息偏差、存储开销）并不足以构成阻碍，且密集表示能简化读取器实现。

@Andrei Tserakhau: 强制密集表示能最小化读取器实现成本，且不阻碍未来扩展；稀疏表示更适合留待未来的“列族”功能作为独立的格式版本引入。

初步结论是强制采用密集表示，Anurag 将在下次同步会议中将其列入议程以正式确认并结束该讨论。

Combine 3 GET calls for parquet reads - Root Manifest, Datafiles and compaction of small files

7 条回复 · 4 位参与者

讨论旨在优化 Iceberg 读取 Parquet 小文件时的 S3 请求效率，提议将原本的 3 次 GET 请求合并为 1 次全文件获取。Varun Lakhyani 提交了 PR 并通过基准测试证明，该方案相比默认实现性能提升约 40%，且比 AWS Analytics Accelerator (AAL) 减少了 HEAD 请求。社区认可了该方案在跨平台兼容性和原生优化上的价值。

@Varun Lakhyani: 提出的 EagerInputFile 方案能将每个文件的请求减少到 1 次 GET，相比 AAL 仍有 8-10% 的性能提升，且适用于 ADLS 和 GCS 等多种存储。

@Steve Loughran: 建议通过 S3 日志精确统计请求数以验证优化效果，并强调在 Manifest 中正确缓存文件大小对于避免重复探测至关重要。

@Daniel Weeks: 倾向于改进原生实现而非过度依赖 AAL，认为这种跨实现通用的解决方案对社区更有价值。

初步结论是该优化方案可行且有效。下一步计划合并该 PR 用于小文件优化，同时结合 Vectored IO 方案处理大文件，并完善文件大小缓存机制。
