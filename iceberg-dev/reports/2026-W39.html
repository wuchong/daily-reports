REST spec: expected server behavior when X-Iceberg-Access-Delegation cannot be satisfied

8 条回复 · 4 位参与者

讨论围绕 Iceberg REST Catalog 规范中 X-Iceberg-Access-Delegation 请求头的语义展开：当客户端请求的访问委托机制（如 vended-credentials、remote-signing）服务器均无法满足时，服务器应返回 200（无凭证）还是 400 错误。讨论中出现分歧：一方主张规范应明确要求返回 400 以实现快速失败；另一方（Daniel Weeks）认为访问控制应由 Catalog 主导，当前规范措辞有意保持宽松，不应强制要求失败。最终发起人接受不修改强制行为，但希望澄清该请求头是能力声明还是强制要求。

@youngrae kim: 提出规范中 'any or none' 表述存在歧义，询问服务器无法满足任何请求机制时是否可返回 400，并表示愿意起草澄清文本。

@Alex Dutra: 主张更新规范，要求当所有请求机制均不可用时服务器应返回 HTTP 400，并指出当前请求头无法表达客户端自带凭证的能力，存在语义模糊。

@Daniel Weeks: 反对修改规范强制返回错误，认为访问委托应由 Catalog 全权决定，当前宽松措辞是有意为之；客户端自带凭证属于反模式，建议通过 Catalog 提供的凭证/签名配置来表达访问方式。

未达成修改规范强制行为的共识。Polaris 将保留其返回 400 的实现选择并作为实现层面行为记录。后续可能的行动是起草一句澄清，说明 X-Iceberg-Access-Delegation 请求头是能力声明还是强制要求，以及缺失该请求头的含义，但不强制规定服务器必须失败。

Catalog-provided metadata tables

8 条回复 · 4 位参与者

讨论围绕是否新增由 Catalog 提供的 .labels 元数据表展开，核心问题是 Iceberg 是否允许元数据表暴露非表元数据、而是 Catalog 侧拥有的信息。Andrei 认为这可支持 SQL 查询和与 .files 等表联查，Ryan 质疑其必要性，Peter 指出这可能与 labels 当前“非持久化、仅当前视图”的设计假设冲突。最终讨论倾向于暂不引入该元数据表，优先通过 SupportsLabels 和 DESCRIBE 等方式暴露 labels。

@Andrei Tserakhau: 提议新增 .labels 元数据表，作为 Catalog 提供元数据的独立类别，便于 SQL 用户、治理工具和 LLM Agent 查询 labels，并可与其他元数据表组合使用。

@Ryan Blue: 不反对通过系统表暴露元数据，但质疑是否必须提供 SQL 表面；认为 labels 主要面向引擎能力，如成本归因或策略附加，不一定需要元数据表。

@Péter Váry: 若将 labels 做成可查询、可联查的元数据表，会使其趋向正式表元数据，与当前 spec 中 labels 不要求持久化、版本化、只表示当前视图的设计不一致。

初步结论是暂不添加 .labels 元数据表；当前更倾向通过 SupportsLabels 编程接口和 DESCRIBE 输出暴露 labels，待后续有更多实际用例后再重新评估。

Reusable encryption keys

7 条回复 · 3 位参与者

讨论围绕 Iceberg 加密密钥设计展开，核心议题是是否应放弃在表元数据 encryption-keys 列表中复用 DEK 的现有模式，改为为每个文件生成独立 DEK 并将加密密钥元数据直接内联到对应文件元数据中。参与者普遍认为 DEK 复用在实践中复杂且收益有限，倾向在 V4 root manifest 和 statistics 文件中采用新的按文件存储密钥元数据方案。

@Gábor Kaszab: 现有 encryption-keys 列表假设 DEK 可复用，但实际因 nonce/AAD 等密码学要求导致复用复杂，建议新文件类型直接将加密密钥存入文件元数据，实现 1-1 映射并简化解密钥清理。

@Gidon Gershinsky: 同意在 V4 中将 DEK 元数据移至按文件结构，每个文件生成随机 DEK 更简单安全；共享的 KEK 仍保留在表元数据的 encryption-keys 列表中。

@Xander Bailey: 支持每文件生成新 DEK，并认可内联密钥元数据带来的清理优势，但关注与现有 manifest-list 模式的一致性，最终被长期维护成本和清理便利性论证说服。

初步达成共识：不再复用 DEK，V4 root manifest 和 statistics 文件应采用按文件内联加密 DEK 元数据的设计，KEK 仍通过现有 encryption-keys 列表共享；下一步是先敲定规范设计（参考 PR #17533），随后提供 Java 实现，并关注 Rust 实现。
