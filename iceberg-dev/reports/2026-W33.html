Initial IRC changes needed for Iceberg V4

6 条回复 · 4 位参与者

本次讨论围绕 Iceberg V4 所需的初始 REST Catalog 规范变更展开，重点是如何在引入 V4 元数据变化（如 Snapshot 中 root-manifest/manifest-list 调整、表位置字段放宽等）时保持向后兼容。多数参与者倾向于通过新增版本化的 `v2::loadTable` 端点来承载 V4 表加载，而不是在现有 v1 端点中混入不兼容响应。

@Daniel Weeks: 认为更干净的方案是新增 `v2::loadTable` 端点，并要求所有 V4 表必须通过该端点加载；仅 loadTable 需要版本升级，commit 仍可复用现有快照更新机制。

@Amogh Jahagirdar: 支持显式 v2 端点方案，认为 V4 变化较大，且未来可能引入 check constraints、default expressions 等更丰富语义，因此新版本 API 能提供更清晰的兼容性边界。

@Yufei Gu: 认同 v1 端点不应返回违反既有 schema 的 V4 元数据，建议 v1 `loadTable` 对 V4 表返回明确错误，同时可借 v2 端点收集其他需求，但部分元数据加载等特性是否纳入仍需谨慎。

初步共识是引入新的 `v2::loadTable` 端点来支持 V4 表，v1 `loadTable` 不应返回 V4 元数据，而应返回明确错误。下一步需要继续明确 V4 还需哪些元数据变更，以及新端点的引入和演进方式。

Dedicated sync for Iceberg Finer Grained Read Restrictions

1 条回复 · 2 位参与者

本次讨论围绕 Iceberg 细粒度读取限制（Finer Grained Read Restrictions）的专用同步会议展开，重点确认嵌套字段策略是否禁止祖先与后代重叠、是否引入能力协商机制，并评估三个端到端 POC 的实现可行性。会议整体认为方向正确，倾向于禁止策略重叠且不进行能力协商，以确保安全治理的严格性和互操作性。

@Sung: 提出禁止在同一个祖先-后代层级上同时下发策略，并指出业界主流系统大多不支持重叠策略，优先级机制会引入额外语义负担。

@Laurent: 认为冲突解决应由 catalog 负责，安全与治理场景应允许 catalog 尽可能严格；不支持能力协商，避免客户端降级到弱策略。

@Russell: 支持不进行能力协商，指出若客户端可选择不同策略表示，可能引发类似 TLS 降级攻击的安全风险。

初步结论是禁止嵌套字段策略重叠，不引入能力协商，采用单一策略表示并在不兼容时返回明确错误；后续需确认是否存在禁止重叠无法覆盖的场景，并继续推进 POC 验证。

Sort-key overlap that size-based compaction cannot see (#17489, PR #17504)

1 条回复 · 2 位参与者

讨论围绕 Iceberg 中基于大小的压缩无法发现排序键重叠的问题展开，即文件大小健康但排序键存在重叠时，rewrite_data_files 不会触发排序压缩，导致聚簇质量无法改善。Heekyung Kim 提出 PR #17504，新增 compute_sort_order_stats 存储过程和 min-overlap-depth 可选排序策略，用于检测并按重叠深度选择需要重写的文件。

@heekyung Kim: 提出通过 compute_sort_order_stats 报告每个分区的排序键重叠深度，并引入 min-overlap-depth 选项，使压缩可以选择重叠严重的文件进行重写，默认行为保持不变。

@Anurag Mantripragada: 认可需要更好的排序文件选择标准，表示愿意参与 review 并联系其他相关人员，但质疑用户如何确定 min-overlap-depth 的合理阈值以维持健康的排序状态。

初步方向获得关注，Anurag 表示将参与 review 并推动讨论，后续需在 PR 中进一步明确 min-overlap-depth 的使用方式和阈值设定方法。

@Péter Váry: 提出并总结了索引设计共识：使用 Iceberg 表达式列表定义 index_keys，不限制函数类型，索引区域文件按 index_keys 生成值排序，并倾向使用 included_column_ids 定义索引区域文件内容。

@Péter Váry: 指出是否将 index_key 表达式结果存入索引区域文件仍存争议：可能有助于读取优化，但也可能冗余并增加文件大小。

@Flavio Junqueira: 质疑该索引提案相对于现有分区裁剪、文件裁剪和 min-max 元数据机制的增量价值，希望明确目标场景。

已就 index_keys 使用表达式定义、不限制函数、索引区域文件排序等达成初步一致；下一步继续讨论是否存储 index_key 表达式结果，该结论可能影响或重新打开 included_column_ids 相关设计。
