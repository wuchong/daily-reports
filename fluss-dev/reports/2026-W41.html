FIP-25: Support In-Place Promotion of Existing Paimon Tables to Datalake-Enabled Fluss Tables

4 条回复 · 2 位参与者

讨论围绕 FIP-25 将现有 Paimon 表原地升级为 datalake-enabled Fluss 表的方案，重点评审 API 命名、失败重试、Bulk Load RPC 和升级期间维护作业的影响。Yuxia 根据 Jark 的意见更新了 FIP，补充了失败处理、Bulk Load RPC 概览、可复用 PbTableInfo 以及快照校验策略。目前主体方向基本获得认可，但 Bulk Load RPC 的实现细节、并发写入隔离和事务恢复机制仍需继续完善。

@Jark Wu: 建议将 API 从 createTableOnLake 改为 createTableFromLake，并要求明确作业提交失败后的重试恢复、Bulk Load RPC 接口、可复用 PbTableInfo，以及 compaction/clustering 是否会影响升级过程。

@yuxia: 已更新 FIP：重命名 API 和 RPC，说明失败后可通过同一 CALL 复用已有表进行恢复，补充 Bulk Load RPC 与 PbTableInfo，并澄清 compaction、clustering、统计任务可继续但应用写入必须停止。

@Jark Wu: 进一步要求明确 Bulk Load RPC 由 Coordinator 还是 TabletServer 处理、是否需要写入隔离或 fencing、如何恢复废弃事务，并建议采用乐观并发模型以及用表级 snapshot_id 和分区信息支持多分区加载。

FIP 已根据首轮评审完成主要更新并获得初步认可，下一步需要补充 Bulk Load RPC 的详细消息设计、职责划分、并发写入隔离、废弃事务恢复方案以及多分区快照信息模型。

FIP-53: Log Scanner Offset Management

0 条回复 · 1 位参与者

本次讨论围绕 FIP-53: Log Scanner Offset Management 展开，核心意见是该提案应聚焦 offset management，而将 consumer group membership 和 rebalancing 拆分为后续议题。Jark Wu 对命名、配置、RPC、错误码、删除语义以及 Scanner API 提出了具体修改建议，强调应尽量复用 Fluss 已有机制并采用对 Kafka 用户更友好的术语。

@Jark Wu: 建议统一使用 “consumer group” 术语，并将相关组件命名为 sys.consumer_offsets、ConsumerGroupManager、FindConsumerGroupOwner 等，以便 Kafka 用户理解并减少与 Fluss Coordinator 的混淆。

@Jark Wu: 认为当前配置、RPC 和错误码仍混入了 membership/rebalancing 及遗留 Kafka 设计，建议改为 Fluss 风格配置，移除不必要字段，并复用现有错误码与 KV 恢复、RocksDB compaction 等机制。

@Jark Wu: 建议澄清 tombstone 删除语义，复用 Fluss 原生 KV delete 路径；同时认为现有 subscribe 已支持 bucket 选择和 offset 更新，应重新考虑额外 assign/seek API 的必要性。

初步结论是 FIP-53 应继续聚焦 offset management，后续需根据命名、配置、RPC、删除语义和 Scanner API 等反馈修订提案，并进一步澄清 tombstone 删除及是否新增 assign/seek 接口。
