FIP-54: Introduce client.writer.delivery-timeout to Fluss Write Client

1 条回复 · 2 位参与者

该邮件讨论围绕 FIP-54 为 Fluss Write Client 引入 client.writer.delivery-timeout 配置，核心议题是批次在累积队列和 in-flight 状态下的超时过期处理，以及幂等写入中序列号连续性如何保障。Sagar 解释了未分配序列号的队列批次可直接过期，已分配序列号的批次过期后将通过 resetWriterId 重置 writerId/epoch 以避免序列错误；Zhe Wang 认可该设计，但进一步关注 writer-id 初始化或重置期间过期扫描可能被阻塞的问题。

@Sagar: delivery-timeout 从批次创建时开始计时，后台 Sender 会扫描累积队列和 in-flight 批次，超时批次将以 TimeoutException 失败；已分配序列号的批次过期会触发 resetWriterId，从而避免序列间隙。

@Zhe Wang: 认可 in-flight 批次独立过期、显式 flush() 契约和 Java API 测试，但担心 Sender.runOnce() 中 initWriter(...).get() 无超时等待会阻塞后续过期扫描，导致批次可能超过 delivery deadline 仍未失败。

@Zhe Wang: 建议在 FIP 中说明 writer-id 分配/重新获取及同步元数据刷新期间如何持续执行过期扫描，并增加测试覆盖 InitWriter future 永不完成时记录仍能按 deadline 失败的场景。

初步共识是 delivery-timeout 应作为从批次创建开始的端到端超时边界，并通过重置 writerId 保障幂等序列安全；下一步需要在 FIP 中澄清 writer-id 获取/重置和元数据刷新期间的过期扫描机制，并补充相关测试用例。

@Prajwal Banakar: 建议让用户直接声明 BITMAP 列，而不是使用 BYTES，底层映射到现有 rbm32 存储，并配合 aggregation merge-engine 使用。

@Prajwal Banakar: Flink 2.3 路径下的 rb_ 函数可原生接收和返回 BITMAP，从而减少算子间序列化/反序列化开销。

@Prajwal Banakar: 实现需要处理 DDL 关键字、Fluss 类型系统扩展以及 Flink connector 兼容性问题，尤其是 fluss-flink-common 仍基于 Flink 1.20 编译。

邮件中尚未形成最终结论，当前处于方案提出和代码影响分析阶段；下一步预计围绕类型系统兼容性和 Flink 2.3 特定实现方式继续讨论。

Kafka Consumer Protocol Compatibility

0 条回复 · 1 位参与者

讨论围绕 Fluss 兼容 Kafka Consumer Protocol 的提案展开，目标是让未修改的 Kafka 消费者（如 Kafka Connect、Kafka Streams 和普通 KafkaConsumer）能够通过 Kafka listener 读取 Fluss log 表。提案分为两个里程碑：第一阶段支持 assign() 消费者、基本读取和故障恢复，不依赖 FIP-53；第二阶段在 FIP-53 完成后支持消费者组、偏移量提交和再平衡。

@Dionysis Stolis: 提出 Kafka Consumer Protocol 兼容性提案，使 Kafka 消费者能读取 Fluss 数据，复用现有日志读取路径和 DDL 表映射。

@Dionysis Stolis: 第一阶段（Milestone 1）支持 assign() 消费者、seek 操作、长轮询和领导者故障恢复，目标版本 1.1。

@Dionysis Stolis: 对 FIP-53 提出三项需求：存储组协议元数据为不透明字节、按 group_id 分桶偏移量表、添加可选的 leader_epoch 字段。

提案已发布供社区评审，第一阶段可独立实施，第二阶段依赖 FIP-53 的完成，需进一步讨论 FIP-53 的适配需求。
