FIP-41: Fluss Kubernetes Operator

2 条回复 · 2 位参与者

讨论启动了关于 FIP-41（Fluss Kubernetes Operator）的提案，旨在弥补现有 Helm Chart 在生产运维（如滚动升级、缩容安全、故障恢复）中缺乏运行时感知的不足。Lorenzo 提议开发 Operator 以实现自动化状态协调，Michael 询问了技术选型与版本支持，Lorenzo 确认将采用 Java Operator SDK 并建议 Kubernetes 最低版本为 1.29。

@Lorenzo Affetti: 现有 Helm Chart 无法感知运行时状态，难以安全处理生产环境中的滚动升级、缩容和故障恢复等操作，需引入 Operator 进行自动化管理。

@Michael Koepf: 支持该提案，并询问具体的实现框架计划（Java Operator SDK 还是 fabric8）以及 Kubernetes 的最低支持版本。

@Lorenzo Affetti: 确认将使用 Java Operator SDK (JOSDK) 以利用其成熟的工作流原语，并提议 Kubernetes 最低版本定为 1.29 以平衡上游支持与企业需求。

初步确定技术选型为 Java Operator SDK，Kubernetes 最低版本倾向于 1.29，后续将把这些细节整合进 FIP 文档。

FIP-32 Multiprotocol Query Gateway for Apache Fluss

@Junbo Wang: 建议在网关层引入基于 TTL 的元数据缓存，以确保 DDL 变更及时可见，而非仅依赖错误驱动的刷新机制。

@Junbo Wang: 指出 PostgreSQL Wire Protocol 的有状态特性，建议采用共享 Catalog 配合连接级会话隔离的分层设计，并优先支持 Flight SQL、PG Wire 和 REST。

@Hongshun Wang: 澄清当前 FIP 范围主要聚焦于查询能力，而非类似 Pulsar Broker 的全功能代理服务，但未来可能演进。

目前处于设计讨论阶段，暂无最终结论，后续需针对缓存策略、会话管理架构及协议支持优先级进行进一步探讨。
