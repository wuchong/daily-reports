Unifying DescribeCluster and DescribeTabletServers

7 条回复 · 4 位参与者

讨论围绕将 DescribeCluster 与 DescribeTabletServers 合并为统一的 Admin.describeCluster() RPC/API，以便一次性获取服务器节点、标签和副本负载信息。社区普遍支持在 1.1 发布前完成合并，避免同时暴露两个重叠接口，并认可默认返回节点与统计信息以保持接口简单。讨论还关注 getServerNodes 的兼容性、授权检查、统计聚合开销及 coordinator 事件队列压力。

@Jark Wu: 提议合并两个接口为统一的 DescribeCluster / Admin.describeCluster，默认返回 coordinator、tablet servers 和副本统计，以减少运维调用和结果拼接成本。

@Nicholas Jiang: 支持统一 API，但建议提供 ClusterDescription 并支持按 server ID 查询，明确区分统计不可用与零副本，同时验证 getServerNodes 的授权和发现行为。

@yunhong Zheng: 支持在 1.1 前完成合并并认领实现；强调 getServerNodes 应保持既有发现语义和权限，关注 coordinator 事件队列压力，建议后续由 tablet server 分担或使用快照优化。

初步结论是在 1.1 前统一为 Admin.describeCluster()，并保留 getServerNodes 的既有行为；yunhong Zheng 已提交 PR #4901 推进实现，后续需补充授权、重试和发现路径测试，并评估统计聚合对 coordinator 的影响。

FIP-25: Support In-Place Promotion of Existing Paimon Tables to Datalake-Enabled Fluss Tables

0 条回复 · 1 位参与者

讨论围绕 FIP-25 将现有 Paimon 表原地升级为 Datalake-enabled Fluss 表的修订提案，重点回应 RPC 归属、写隔离和事务发现/并发问题。Yuxia Luo 说明新方案由 Coordinator 负责 BulkLoad 事务接口，TabletServer 通过 NotifyLeaderAndIsr 完成 fencing、空目标检查和快照恢复。提案初版倾向于按物理目标严格串行，并提供查询与恢复机制处理未完成事务。

@Yuxia Luo: BeginBulkLoad、CommitBulkLoad、AbortBulkLoad 和 GetInProgressBulkLoad 由 Coordinator 处理，TabletServer 通过 NotifyLeaderAndIsr 参与 fencing、检查 bucket 是否为空并恢复快照。

@Yuxia Luo: Begin 会将目标置为 LOADING，期间拒绝普通写入和外部数据访问；扩展 NotifyLeaderAndIsr 字段以支持隔离、空目标检查和提交后的快照恢复，且该 fencing 设计不会延后。

@Yuxia Luo: GetInProgressBulkLoad 可根据物理目标查询当前事务状态和句柄，便于处理废弃事务；初版建议保持每个物理目标严格串行，因为并发准备会增加复杂度且收益有限。

初步结论是写隔离和 fencing 作为核心设计纳入提案，初版采用严格串行策略；下一步可基于该修订方案继续推进实现与评审。
