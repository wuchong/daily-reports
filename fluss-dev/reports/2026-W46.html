FIP-64: Support Log Tables with Deduplication Keys

8 条回复 · 4 位参与者

讨论围绕 FIP-64 为日志表支持去重键展开，目标是在保留追加和日志读接口的同时，通过复用主键写机制并仅保存键存在标记来实现业务事件去重。社区重点讨论了表模型定位、写路径性能、基准测试、读侧去重与分桶扩展性，提案已根据反馈更新语义、兼容设计并补充基准数据。

@Yang Wang: 提出日志表支持去重键，仅保存存在标记以降低存储；已更新键/分区语义、PRODUCE_LOG 兼容和 Arrow/DV 设计，并补充基准，仍开放是否支持按 key 检索保留行。

@Jark Wu: 建议明确该能力应作为日志表去重还是主键表存储选项，并要求基准验证；后续指出精确去重比普通日志表吞吐低 28%-36%，建议扩展 PutKv 以复用压缩 Arrow 负载来优化写路径。

@Jim Hu: 关注低重复率场景下写路径开销，提出可探索读侧 merge-on-read 取舍，并询问分桶数、键基数和保留期对扩展性的影响。

初步方向是保留日志表去重语义并继续通过基准驱动优化写路径；下一步包括完善 FIP、评估 PRODUCE_LOG/服务端去重、Arrow 负载复用、读侧去重，以及决定是否支持按 key 检索保留行。

FIP-62: Support tiering Fluss data to Delta Lake

6 条回复 · 3 位参与者

讨论围绕 FIP-62：在 Fluss 中支持将数据分层存储到 Delta Lake，第一阶段聚焦 log 表，并通过 Delta Kernel API 写入 Parquet。社区已验证 PR #4944 的基本可行性，并重点讨论 Flink 读取、Schema 演进、Compaction 和 Delta 表复用等问题。目前方案方向获得认可，FIP 已根据反馈更新。

@Jaejun Lee: 提出并推进 FIP-62，确认第一阶段采用 LakeSource 支持 Flink 读取，明确 Schema 演进和 Compaction 暂不作为第一阶段能力，并承诺在 CREATE TABLE 时拒绝复用非空 Delta 表。

@Anton Borisov: 认可基于 Delta Kernel 和分阶段实现的方向，本地验证 PR #4944 可读写，并提出 Flink 读取、Schema 演进、Compaction 与历史恢复等关键问题。

@Zhe Wang: 指出 Fluss 表删除后重建可能复用旧 Delta 表并读取到历史数据，建议第一阶段拒绝复用非空 Delta 表，但允许复用失败创建留下的空表。

初步结论是继续推进 FIP-62，第一阶段实现 Delta Lake tiering 和 log 表 LakeSource 读取，暂不支持 Schema 演进与 Fluss 自主 Compaction；下一步将根据讨论更新 FIP 和 PR #4944，并补充 Delta 表复用校验。

FIP-60: Extend Schema Evolution with Drop, Rename, Type Widening, and Nested Additions

4 条回复 · 3 位参与者

讨论围绕 FIP-60 扩展 Fluss 模式演进，支持删除、重命名、类型扩展和嵌套字段新增，并强调不重写历史数据、通过 field ID/schema version 保持字段一致性。社区重点评审了分阶段实施、升级降级兼容、运行作业影响、投影下推以及 Lake 集成元数据复杂度，作者已据此更新提案。

@Hongshun Wang: 提案在不重写历史数据的前提下扩展 schema 演进，并采用 field ID、schema version 和 Lake-First 发布来保持字段身份与恢复一致性；后续同意分阶段推进并简化持久化元数据。

@Giannis Polyzos: 建议将 FIP 拆分为可独立发布的阶段，明确升级/降级和客户端兼容性，评估 DROP/类型扩展对运行作业的影响，并保留投影下推与补充各 Lake 后端细节。

@Yuxia Luo: 担心持久化完整 lake mapping 和 native schema 引入过多复杂度，建议初期禁止同一 ALTER 中混合 ADD/DROP，并复用现有 schema 比较机制简化恢复。

初步方向是分阶段交付，并在 lake 表上限制同一 ALTER 混合 ADD/DROP；作者计划保留紧凑的 fieldIdMapping、移除完整 native schema 持久化，继续完善 Flink/非 Lake 阶段和 Lake 集成细节后再推进评审。

FIP-61: Snapshot-Based Bulk Loading for Primary Key Tables

2 条回复 · 2 位参与者

本次讨论围绕 FIP-61 为主键表引入基于快照的 Bulk Loading，以替代高成本逐行初始加载，实现批量构建历史状态后切换流式更新。Giannis 提出批流转接中的源位点记录、merge engine 表支持及下游读取问题；Yang 认为 BulkLoad 协议应保持通用，由上层初始化作业管理源位点，merge engine 支持需进一步重构。社区初步认可该方向，并计划后续推进，尤其关注 partial update 等合并引擎场景。

@Giannis Polyzos: 支持 Bulk Loading，并关注批转流时记录源位点、是否支持 partial update/aggregation 等 merge engine 表，以及无 changelog 时下游读取的问题。

@Yang Wang: 源位点应由上层初始化作业管理，关联源快照、增量起点和 BulkLoad ID，以保持 BulkLoad 协议独立于具体数据源。

@Yang Wang: merge engine 支持是有价值方向，但当前实现与服务端耦合，需要重构；'last row wins' 仅用于构建输入去重，不代表目标表只能覆盖。

初步结论是 BulkLoad 适用于大规模初始加载并转向流式更新；下一步将探索 merge engine 支持，partial update 可能作为较易落地的首个方向。
