Log Enrichment via Append Columns

0 条回复 · 1 位参与者

Keith Lee 提议通过“追加列”机制优化日志富化流程，旨在解决当前架构中因数据双写导致的存储和 I/O 成本倍增问题。该方案允许将富化列直接写回原日志表，并通过水位线机制确保读取数据的完整性，目前已提交 FIP 文档及 POC 代码供社区评审。

@Keith Lee: 现有架构将数据写入两个表导致基础列重复存储，造成存储和 I/O 资源浪费。

@Keith Lee: 提议引入“追加列”原语，支持将富化列写回原表，实现基础列与富化列的独立存储与读取。

@Keith Lee: 系统利用富化水位线（EWM）限制读取进度，确保消费者仅能读取到已完成的完整数据行。

已发布 FIP-45 提案及 POC 实现，正在征求社区意见。

FIP-41: Fluss Kubernetes Operator

0 条回复 · 1 位参与者

讨论主要围绕 FIP-41 Fluss Kubernetes Operator 提案展开，参与者总体支持该方向，但指出了在集群重平衡、PVC 生命周期及滚动升级安全性方面的不足。建议完善扩缩容流程、ID 分配机制及副本恢复门控逻辑，以奠定良好的 Operator 基础。

@Giannis Polyzos: 扩容后需触发重平衡，缩容需先执行排空路径（标记临时下线+重平衡+验证零桶）以防集群不可用。

@Giannis Polyzos: 建议由 Operator 负责 ID 分配以避免 PVC 回收导致 ZK 状态损坏，并明确 PVC 不自动删除。

@Yunhong Zheng: 滚动升级规范不足，Operator 不仅要在退出时处理 Leader 迁移，还必须在进入时等待副本恢复完成（如日志追上、桶加入 ISR）。

提案总体获支持，但需针对重平衡触发机制、PVC 生命周期及滚动升级中的副本恢复门控进行完善。
