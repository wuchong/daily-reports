FIP-68 Cluster Feature Versioning

1 条回复 · 2 位参与者

讨论围绕 FIP-68 Cluster Feature Versioning 展开，目标是解决 Fluss 在滚动升级中无法安全启用新日志格式等能力的问题。提案参考 Kafka KIP-584，将二进制升级与特性启用分离，通过 ZooKeeper 记录最终特性级别、Admin API 提升级别，并让客户端感知集群特性版本。目前已有概念验证，正在征求社区对整体方案的反馈。

@Dionysis Stolis: 提出 FIP-68：通过集群特性版本化机制，确保新能力只在所有服务器都支持后才启用，避免升级期间写入旧节点无法读取的数据；方案包括 ZooKeeper 存储最终特性级别、Admin API 提升级别、级别只升不降，并已在分支中提供 PoC。

@Yang Wang: 建议在协议层面为未来条件降级预留空间：ApiVersions 可返回 feature epoch，客户端根据更高 epoch 更新缓存，而不是假设特性级别永远单调递增。

@Yang Wang: 建议 Admin API 的 updateClusterFeatures 返回 feature epoch，而不是 CompletableFuture，以便调用方跟踪特性变更是否已被 TabletServer 应用。

目前尚未形成最终结论，但初步方向是支持特性版本升级、暂不支持降级；下一步是继续讨论整体设计，并评估引入 feature epoch、客户端缓存策略和 Admin API 返回值等改进。
