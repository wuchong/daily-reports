FIP-41: Fluss Kubernetes Operator

1 条回复 · 2 位参与者

讨论主要围绕 FIP-41 Fluss Kubernetes Operator 的实现细节展开，重点探讨了缩容/下线机制及滚动升级流程中的潜在问题。参与者一致认可总体方向，但指出当前方案在服务器端 API 依赖和 Pod 就绪状态定义上存在不足，需进一步完善。

@Anton Borisov: Path A 和 Path B 均需服务器端改动，现有的 Rebalance API 存在 min-ISR 风险及多步操作崩溃恢复问题，建议新增 DecommissionServer API 进行封装。

@Yunhong Zheng: 滚动升级不应仅依赖进程启动状态，需将 Pod 就绪定义为“完全恢复”（日志追赶、KV 恢复等），建议使用 Pod readiness gate 机制。

@Yunhong Zheng: 升级过程应增加双重门槛：上一节点完全恢复且集群满足稳定性条件（如 min-ISR），以避免在状态恢复期间进行后续重启。

初步结论是需要完善服务器端 API（如 DecommissionServer）并重新定义 Pod 就绪标准（引入 readiness gate），下一步需针对这些具体实现细节进行补充设计。
