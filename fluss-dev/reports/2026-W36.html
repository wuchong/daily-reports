FIP-44: Enhanced LanceDB Integration — Vector Indexes, FTS, and Hybrid Search

2 条回复 · 2 位参与者

本讨论围绕 FIP-44（增强 LanceDB 集成：向量索引、全文检索与混合搜索）展开，重点澄清了向量数据类型在零拷贝范围、维度定义与校验、NULL 语义及兼容性等方面的设计细节。Mehul 已认可大部分方案，并建议先聚焦 VECTOR(n) 数据类型本身，将相似性函数、ANN/KNN 索引、混合读取语义等拆分为后续独立提案。目前整体方向趋于收敛，但仍需完善校验机制、Flink 层类型映射及客户端兼容性等细节。

@Sagar: 零拷贝仅保证在原生列式分层管道（Fluss Arrow Log -> Arrow FixedSizeListVector -> Lance Dataset）中，行式写入和 Flink SQL 查询仍使用标准序列化；POC 已实现 Vector(n) 作为一等类型参数，并在写入边界强制校验维度。

@Mehul Batra: 建议首个 FIP 仅聚焦 VECTOR(n) 数据类型，而将相似性 UDF、ANN/KNN 索引、混合读取语义和多维支持拆分为后续提案；同时要求统一维度校验逻辑并明确服务端是否校验。

@Mehul Batra: 指出 Flink 层使用 ARRAY 可能导致插入失败，因为多数管道生成可空元素，Flink 不会隐式转换为非空，需验证并明确是添加隐式转换还是要求用户显式 cast。

初步共识是将首个 FIP 范围限定为 VECTOR(n) 数据类型本身，后续功能分拆为独立提案；下一步需统一校验逻辑、验证 Flink 插入兼容性，并通过社区会议和 Google Doc 对齐设计细节后推进 FIP。

FIP-25: Support In-Place Promotion of Existing Paimon Tables to Datalake-Enabled Fluss Tables

2 条回复 · 3 位参与者

本次讨论围绕 FIP-25 展开，该提案支持通过 CALL sys.enable_fluss_on_lake_table(...) 将已有 Paimon 表原地升级为启用数据湖能力的 Fluss 表，复用原表和存量数据。社区重点关注长时间 Bulk Load 下的超时与状态查询、失败重试与恢复机制，以及迁移期间写入可用性和数据一致性保障问题。

@yuxia: 提出 FIP-25，主张在不重建表、不重写数据的前提下，通过存储过程原地升级 Paimon 表，并在必要时通过 Bulk Load 初始化主键状态、校验 schema 与快照一致性。

@Liting Liu: 建议为长时间运行的升级操作引入操作 ID 和状态查询机制，并持久化快照 ID、分区、Bulk Load 事务 ID 等信息，以明确超时、取消、失败重试和恢复语义。

@Zhe Wang: 关注生产迁移期间的写入中断和数据正确性，建议区分基线加载与最终写入切换，或至少明确离线迁移限制、写入停写时长及失败恢复方案。

目前尚未形成最终结论，但讨论方向集中在补充超时/取消/重试语义、增强失败恢复可观测性，以及明确迁移期间写入限制和一致性保障机制。

@Anton: 作为提案作者，对 FIP-50 进行了修订并澄清了相关设计细节，接受了关于分阶段实施和架构边界的建议。
