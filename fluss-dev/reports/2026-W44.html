FIP-31: Introduce Deletion Vectors to accelerate Primary Key Table Union Read over Iceberg

4 条回复 · 3 位参与者

社区围绕 FIP-31 中 Iceberg 删除向量方案展开讨论，重点是比较基于 RowId 的删除索引与基于主键索引并派生删除掩码的方案。多位参与者认可主键索引可避免额外系统列、支持外部引擎写入或重写文件，并能让数据与删除在同一快照中提交。讨论已从方案对比推进到恢复语义、日志保留和提交防护等契约细节。

@Anton Borisov: 主张以主键而非 RowId 作为索引键，认为这可避免 __rowid 系统列、支持外部引擎写入或重写的数据被正确屏蔽，并可在同一 Iceberg 提交中完成数据写入与删除。

@Nicholas Jiang: 认可主键索引加派生删除掩码的方向，但强调需要明确快照语义、重复更新、删除后重插、恢复行为，并补充日志保留和 tiering epoch fencing 等契约。

@Giannis Polyzos: 倾向 derived design，认为每个 lake snapshot 应自洽，主键是自然行标识，从索引和日志派生删除掩码更易保证正确性，也能兼容不同 Iceberg 格式版本。

初步共识是优先探索基于主键索引和派生删除掩码的方案；下一步需要在 FIP 中完善恢复模型、日志保留、提交防护、Paimon 配置校验和回归测试。

FIP-59 Kafka Idempotent Produce

2 条回复 · 2 位参与者

本次讨论围绕 FIP-59 如何支持 Kafka 幂等写入 Fluss，核心问题是采用新增 V3 批格式统一承载 epoch 和 sequence，还是保持现有格式并在服务端特殊处理 Kafka writer。目前讨论明显倾向于 Option A，认为其不仅支持 Kafka 幂等与事务，也能服务原生 Fluss writer 并为未来格式演进铺路。

@Dionysis Stolis: 提出 Option A 与 Option B 两种方案，并指出 Kafka 事务依赖 epoch 做隔离，因此 Option A 比在服务端隐藏编码 writer ID 的 Option B 更可维护。

@Yang Guo: 支持 Option A，认为 writer epoch 对原生 Fluss writer 也有价值，可帮助解决 CDC 恢复后状态过期导致的序列错误，并且便于未来扩展如事件时间等格式能力。

@Dionysis Stolis: 建议为存储格式演进启动单独 FIP，并让 V3 格式成为该机制下的首个变更，同时征询社区是否反对 Option A。

目前初步倾向采用 Option A；下一步是继续征询社区反对意见，并考虑推进单独的存储格式演进 FIP，以便在目标版本中落地 V3 格式。

FIP-47: Introduce Deletion Vectors to accelerate Primary Key Table Union Read over Paimon

0 条回复 · 1 位参与者

讨论围绕 FIP-47 在 Paimon 主键表联合读取中引入 Deletion Vectors 的设计展开，重点关注分区过期、快照过期、RowPos SST 保留与恢复一致性等问题。Anton Borisov 基于 FIP-31 提出了若干 Paimon 场景下的补充疑点，认为当前设计仍需明确清理与保护机制。

@Anton Borisov: 在启用分区过期和自动快照过期时，被 OVERWRITE 删除的分区文件可能仍残留 LakeDv 和 RowPosIndex 条目，当前仅收集 COMPACT 快照文件变更可能无法覆盖该场景。

@Anton Borisov: RowPos SST 的可读 round 保留策略尚不明确，建议在所有 bucket checkpoint 追上后删除；如果恢复时发现 round 缺失，应失败而不是继续。

@Anton Borisov: 快照过期需要保护可读快照及其文件，但当前设计缺少类似 Iceberg tag 的强制保留机制，且 compaction 提交可能触发 Paimon 默认快照过期。

目前尚未形成最终结论，需要进一步澄清并补充 Paimon 场景下的过期清理、RowPos SST 保留和可读快照保护机制，下一步预计由设计者回应并继续推进 FIP 讨论。
