FIP-54: Introduce client.writer.delivery-timeout to Fluss Write Client

0 条回复 · 1 位参与者

该邮件讨论围绕 FIP-54 引入 client.writer.delivery-timeout 配置，核心议题是 Fluss 写客户端如何在批次超时后可靠过期并保证语义一致。Zhe Wang 认可了对 in-flight 批次独立过期、显式 flush() 契约和 Java API 测试的回应，但进一步提出在 writer-id 初始化/重置或同步元数据刷新期间，过期扫描可能因阻塞而无法持续运行的问题。Sagar 表示可根据反馈更新 FIP，并在无进一步问题后发起投票。

@Zhe Wang: 关注 writer-id 分配或重置期间若 initWriter RPC 未完成，Sender 可能无法继续执行过期扫描，导致排队批次超过交付期限；建议 FIP 明确该场景并补充测试。

@Sagar: 解释了幂等性和序列号机制：在 accumulator 中尚未被 drain 的过期批次未分配序列号，因此可安全中止；并表示会根据反馈更新 FIP。

讨论已接近收敛，Sagar 计划根据 Zhe Wang 的剩余问题更新 FIP，若无进一步异议将开放投票。

FIP-53: Log Scanner Offset Management

0 条回复 · 1 位参与者

Fluss 社区围绕 FIP-53: Log Scanner Offset Management 展开讨论，重点是如何拆分提案范围并明确 offset 存储、读取一致性和提交原子性设计。作者已根据评审意见将原提案拆分为三个独立 FIP，并计划优先推进低风险的 offset 存储与手动分配核心能力。

@jie lu: 同意拆分 FIP，已将提案分为 FIP-53（offset 存储、手动 assign、OffsetCommit/OffsetFetch 和 Admin 操作）、后续组成员与 rebalance 协议、Flink/Kafka 兼容集成三个独立部分。

@jie lu: 明确 offset 存储保证：同一 group 的 offset 行落在同一 offsets 系统表 bucket，OffsetFetch 由 coordinator 从内存状态读取，并在 requireStable 下对未稳定提交返回 UNSTABLE。

@jie lu: 多 bucket 提交具有原子性，因为同一 group 的 offsets 会打包为单个 KvRecordBatch 进行一次 append，成功或失败都会整体生效并返回一致结果。

初步结论是优先推进拆分后的 FIP-53 核心存储设计，将组成员和 rebalance 协议移到单独 FIP 继续深入讨论。
