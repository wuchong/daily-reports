FIP-49: Fluss Gateway REST API

7 条回复 · 5 位参与者

讨论主要围绕 FIP-49 Fluss Gateway REST API 的技术选型、架构设计及授权模式展开。社区重点讨论了为何选择 Rust 而非 Java/Netty、如何隔离查询与写入的资源竞争，以及 Service 与 User 两种模式下的授权边界，目前已完成 PoC 并准备进入投票阶段。

@Liting Liu: 质疑为何不使用 Java/Netty 栈，并担心 DataFusion 查询可能耗尽资源影响写入稳定性，建议初期仅提供轻量级查找 API。

@Junbo Wang: 解释选择 Rust 是为了实现零拷贝和低延迟，确认初期仅支持轻量级查找，查询将通过独立线程池和内存限制进行隔离。

@Leonard Xu: 建议明确 Service 模式（共享服务账户）与 User 模式（需 Act-as 支持）的授权边界，并支持将原生操作与 SQL 路径分离的架构方向。

社区对提案方向达成共识，确认 FIP-49 将聚焦于基于 fluss-rust 的原生写入和轻量级查找，作者已更新提案并提交 PoC，计划启动投票流程。

FIP-32 Multiprotocol Query Gateway for Apache Fluss

4 条回复 · 3 位参与者

讨论旨在推进 FIP-32（多协议查询网关）纳入 1.0 版本，核心议题是如何界定其范围与架构边界。经过讨论，社区倾向于缩小 FIP-32 的初期范围，并明确其与 FIP-49（REST 网关）的职责分工，以便更快交付。

@Keith Lee: 建议明确将认证授权排除在范围外，并缩减初期支持的协议数量（仅保留 ArrowFlight 和 REST），以加快交付速度。

@Junbo Wang: 支持缩减范围，指出 Arrow Flight SQL 依赖尚未就绪的 fluss-datafusion，建议初期仅专注于 REST，待依赖成熟后再引入 Flight SQL。

@David Reger: 提出架构原则：FIP-49 应专注于原生操作的 REST MVP，而 FIP-32 专注于查询架构，两者应共享底层基础设施以避免实现分裂。

初步达成共识：FIP-32 将作为多协议 SQL 查询网关的父 FIP，FIP-49 则专注于原生 Fluss 操作的 REST 支持。社区将优先致力于 FIP-49 的实现，以此引领 REST 网关及共享组件的设计。
